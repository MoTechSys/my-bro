# 03 — خارطة التنفيذ الموحدة من الاستلام إلى التسليم

> المالك ASTRA؛ تحديث 2026-09-09؛ الحالة خطة تنفيذ لا تقرير نجاح. الحاكم docs/05؛ الحالة الحية STATE/TASKBOARD؛ الأدلة TEST_PLAN وTAKEOVER_AUDIT. ADR-011/012 لا يغيران النطاق.

## 0. أولوية المستخدم الجديدة: الدراسة قبل متابعة التنفيذ

T-17/PR #22: [دراسة الأصول والمخطط المقترح](INTENT_STUDY_AND_BLUEPRINT.md). أول خطوة عرض D1–D7 وحسم نية الهواتف/أجهزة الشبكة/واجهة مستقلة/AI وتصحيحات FR/NFR. توصية رفع أولوية T-31 ومستوى هاتف تجريبي ليست اعتماداً تلقائياً؛ ADR-013 مقترح. حدود §1 أدناه هي خط الأساس السابق، لا دليل أن الأخ تنازل عن رؤيته. لا تُسقط الأهداف الموسعة بصمت ولا تنفذها دون تفصيل الصلاحيات والقبول.

بعد الدراسة يستمر العمل غير المتنازع عليه في T-11/نواة المشروع؛ ميزات النطاق الجديدة تنتظر قرارها. لا حاجة لإعادة حجز المهام الموجودة أو إسقاط الترتيب والبوابات أدناه.

## 1. حدود المنتج

النواة: Wazuh Manager/Indexer/Dashboard + وكلاء Linux/Windows، Suricata، FIM، VirusTotal/AR، YARA، auditd/CDB، سجلات Apache والعمليات. المساهمة: تكامل قابل للقياس والتكرار مع استجابة مضبوطة، لا محرك كشف جديد ولا وعد بتكلفة تشغيل صفرية.

SHOULD: SSH/firewall-drop (T-13)، SQLi (T-12)، إشعار (T-14). COULD: مصدر syslog واحد (T-31). AI/TheHive/Zeek/الهواتف أعمال مستقبلية خارج التنفيذ الحالي، لا مهام اختيارية تُضاف بلا ADR وموافقة. لا حذف لمتطلب FR/NFR بسبب صعوبة اختباره.

## 3. بوابات P1 التفصيلية (تحفظ المتطلبات القديمة)

- P1.1: توحيد rules/decoders/lists؛ wazuh-analysisd -t وlogtest ثم تنبيهات فعلية (ISSUE-010).
- P1.2: قواعد YARA الدائمة وبصماتها، ثم reboot وتجربة (ISSUE-020).
- P1.3: HOME_NET مرة واحدة، interface حقيقية، suricata -T (ISSUE-021).
- P1.4: كلا الوكيلين active بلقطة حديثة (ISSUE-026).
- P1.5: Windows YARA native أو وصفه غير مختبر؛ لا إسقاط متطلب Windows بصمت (ISSUE-006).
- P1.6: مطابقة المسارات المنشورة مع FIM/allowlists (ISSUE-018).
- P1.7: UID/GID وسياسة auditd المحملة (ISSUE-031).
- P1.8: أدلة حقيقية لكل UC؛ صور توثيق Wazuh ليست نتائج الفريق (ISSUE-005/032).

P0.7: الفاحص المحلي موجود؛ CI غير مفعّل بعد (T-40/ISSUE-038)، فلا توصف مرحلة CI مكتملة.
الفصول 1–3 وTEST_PLAN وDEMO مسودات/وثائق موجودة، لا مهام لم تبدأ؛ تدقيقها وإثبات التنفيذ منفصلان.

## 4. هيكل المستودع ومصدر الحقيقة

- docs/05 للنية؛ docs/02 لحقائق المعمل مع مصدرها وعدم يقينها؛ STATE/TASKBOARD للحالة فقط.
- docs/lab لكل UC: الهدف/الإعداد/السلامة/الاستعادة/المتوقع/الدليل/الأخطاء؛ لا تكرر الكود في الرسالة بلا رابط نسخة.
- wazuh/ مقاطع تدمج بعد المراجعة، لا overwrite لـossec.conf الحقيقي؛ scripts/lab وattack-emulation وmeasure وvalidate بوظائف منفصلة.
- tests/ عقود واختبارات وأدلة نتائج عند توفرها؛ البيانات الاصطناعية fixtures لا نتائج معملية.
- docs/sources أرشيف ثابت؛ docs/thesis مخرجات أكاديمية؛ لا إعادة ترتيب للأصول تكسر روابط اللقطات.
- كل task يترك: ما تغير، الاختبارات، ما لم يختبر، ISSUEs، الخطوة التالية الدقيقة وPR؛ TAKEOVER_AUDIT يسجل تغطية القراءة.

## 5. ما يحتاج الفريق والجدولة

Q5 موعد المناقشة مطلوب؛ لا نفترض مدة تنفيذ للتوسعات. إن اقترب الموعد نعرض إعادة ترتيب نحو T-22/23/25 للموافقة، لا نسقط P3 أو متطلباً بصمت. Q6 القالب شرط قبول التنسيق النهائي. يلزم وصول أو تنفيذ بشري على المعمل، hashes موثوقة، ونشر أدلة منقحة لا مفاتيح API. أداة القياس لا تعوّض غياب مصدر الوقت أو سجل المحاولات.
