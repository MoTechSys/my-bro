كلا الإعلانين يصف قدرات برمجة/عمل معرفي قوية. Astra يصف تحسينات مستندات واستخدام حاسوب وحفظ سياق في Codex؛ هذه ميزات منتج/بيئة معينة، لا قدرات نعلن تفعيلها في كل جلسة. Fable/Mythos يختلفان في الحواجز؛ بعض نتائج Fable المنشورة تستعمل نماذج fallback، وبعض جداول OpenAI تنسب نتائج Mythos إلى Fable بحاشية. لا نحذف تلك الشروط عند المقارنة.

الرفض أو توقف الأداة لا يجيز التحايل أو تدوير الطلب للحصول على إجراء مرفوض. نحدد نطاقاً دفاعياً مصرحاً، أو نستخدم مسار وصول رسمي مناسب، أو نسجل blocker. لا نقول «كل الدفاعي مفتوح»؛ قيود الإنتاج قد توقف عملاً مشروعاً أيضاً.

## 4. توزيع العمل الحالي وخطة استخدام نموذجين عند توفرهما

ASTRA اسم مالك العمل الحالي وفق تسليم #17؛ يملك جميع مهام التنفيذ والتوثيق المتبقية بالحجز. CLAUDE مؤلف ومراجع تاريخي، وليس عاملاً نشطاً مفترضاً. ترتيب الأولوية الآن دراسة T-17 وقراراتها، ثم بقية T-11 والنواة والتوسعات وفق ROADMAP.

إن توفر وصول معتمد لنموذجين: يسلم المنفذ للمراجع نص المتطلب والمصدر والـdiff واختبارات النجاح والفشل، ويطلب نقداً مستقلاً لا مجرد تأييد. تبقى نتيجة المراجع فرضية حتى التحقق. يمكن اختيار Fable أو Astra للتصميم أو التنفيذ أو المراجعة وفق اختبار صغير ممثل للمهمة؛ لا ادعاء أننا شغلنا الاثنين الآن.

حزمة كل مهمة: source refs، ملف/نسخة، acceptance criteria، حدود صلاحية وأسرار، مخرج وtests، ما لم يُختبر، handoff واضح. لا اختصار لمتطلب بسبب ضيق السياق؛ يُنقل للسجل مع حالته. لا نسبة اكتمال من أسماء النماذج أو عدد الأسطر.

**AI للتطوير لا يعني AI في المنتج:** الأول وسيلة بناء ومراجعة؛ الثاني feature جديدة تحتاج موافقة وميزانية وخصوصية وتقييماً. إذا أُقر runtime LLM: تفسير read-only مستند إلى alert IDs، التعامل مع نص السجلات كمدخل غير موثوق، اختبار prompt injection، لا صلاحية shell أو حذف/حظر، وفشل الخدمة لا يوقف SOC.

## 5. قاعدة "لا تشينكس، لا حذف، لا تجاوز" (Zero-Skip Rule)

بتوجيه المستخدم، **يُمنع**:
1. تعليم مهمة ✅ وهي ناقصة — الحالة الصادقة: `◐ IN-PROGRESS` + "المتبقي بالضبط".
2. حذف أو تقليص نطاق متطلب (FR/NFR في ch3 §3.3) دون ADR في `DECISIONS.md` وموافقة المستخدم.
3. تجاوز فحص `validate_all.sh` أو مراجعة الآخر.
4. الادعاء بأن شيئاً "يعمل" بلا دليل مؤرَّخ (ISSUE-032).
5. إغلاق ISSUE بلا ذكر الـ commit أو الدليل.

## 6. هندسة السياق (Context Engineering) — إلزامي لكل جلسة

الهدف: **أي وكيل جديد يقرأ المستودع فقط ويعرف بدقة أين نحن وماذا يفعل** — بلا هلوسة، بلا افتراض.

| الملف | من يُحدّثه | متى | ما يجب أن يحتويه |
|-------|-----------|-----|------------------|
| `docs/00_PROJECT_STATE.md` | من أنهى مهمة | فور الدمج | آخر دمج مثبت، بوابات الإنجاز والأدلة دون نسب تقديرية، **المهمة التالية بالضبط** |
| `docs/TASKBOARD.md` | صاحب المهمة | عند الحجز، وعند الإنهاء، وكل ساعة عمل | الحالة + المتبقي بالضبط + commit |
| `docs/SESSIONS_LOG.md` | كل وكيل | نهاية كل جلسة (append-only) | ما أُنجز، commits، رسائل `@OTHER` |
| `docs/04_ISSUES_LOG.md` | من اكتشف/أغلق | فوراً | ID فريد، الموضع، الإصلاح، الحالة، الـ commit |
| `CHANGELOG.md` | من دمج PR | مع كل PR | نسخة semver + Added/Changed/Fixed |
| `docs/DECISIONS.md` | من اتخذ قراراً معمارياً | قبل التنفيذ | ADR: السياق، القرار، البدائل، العواقب، الحالة |

**قاعدة الـ 60 دقيقة:** كل 60 دقيقة عمل → commit + تحديث TASKBOARD (حتى لو لم تنتهِ المهمة) — لتقليل الضياع عند انقطاع الجلسة.

**قاعدة السطر الأول:** أي ملف جديد يبدأ بـ header: الغرض، المالك، الحالة، آخر تحديث، المصادر.
