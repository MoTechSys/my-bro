## 1. الجواب المباشر

**يمكن استكمال توثيق الفصول 1–3 الآن، لكن معايير الدقة ليست مطبقة بالكامل في النسخة الحالية.** وجود النصوص والمخططات لا يعني اعتماد محتواها نهائياً، ونجاح الاختبارات البرمجية لا يثبت اكتمال المنصة أو التجارب أو سلامة كل ادعاء أكاديمي.

هذه معايير عمل وتدقيق لهذا المشروع، وليست شهادة مطابقة لمعيار جامعي أو اعتماد رسمي. قالب الجامعة ومتطلبات المشرف يحتاجان تأكيد الفريق (Q6). لا تُعطى نسبة إنجاز تقديرية دون قائمة قبول مكتملة وأدلتها.

هذا الدليل يوثّق المطلوب والفجوات؛ **لا يصلح الكود ولا يعيد كتابة الفصول ولا يغلق بوابات القبول المعملي**.

## 3. معيار الإثبات والصياغة

لكل ادعاء مؤثر سجّل: المتطلب، الملف/القسم، المكوّن، حالة الاستخدام، الدليل، تاريخ الدليل، الإصدار/commit، مستوى التحقق، والحدود.

| مستوى الإثبات | ما يجوز قوله | ما لا يثبته |
|---|---|---|
| مصمَّم | «يقترح التصميم…» أو «يستهدف النظام…» | وجود تنفيذ عامل |
| منفّذ في المستودع | «يوجد كود/إعداد لتنفيذ…» | نجاح التشغيل على الجهاز الحقيقي |
| مختبَر محلياً | «اجتاز الاختبارات البرمجية المحددة…» | تحقق التكامل الكامل أو أمان شامل |
| مختبَر على المحرك | «طابقت القاعدة السجل في wazuh-logtest…» | تشغيل الحساس أو الاستجابة على الجهاز الأصلي |
| تكامل بمحاكاة | «اختُبر المسار باستخدام سجل محاكى/نتيجة محقونة…» | تجربة الجهاز أو الخدمة الخارجية الفعلية |
| تحقق حي | «نُفّذ المسار المحدد في البيئة والإصدار المذكورين…» | استمرار عمله الآن أو تعميمه على جميع البيئات |
| قياس منهجي | «أظهرت المحاولات المسجلة النتائج التالية…» | نسبة نجاح أو أداء خارج العينة وشروطها |

عبارات مثل «كل المتطلبات منفّذة»، «لا يحدث ضرر»، «كل ادعاء له استشهاد صحيح» لا تُستخدم كضمانات مطلقة. أهداف NFR ليست نتائج؛ نجاح تشغيل واحد ليس تقييماً إحصائياً.

## 4. متطلبات استكمال كل فصل

### الفصل الأول: المقدمة

- تحديد المشكلة وأسئلة البحث والأهداف والأهمية وحدود المشروع.
- وصف المنتج بأنه طبقة تكامل فوق Wazuh، لا بديل مستقل أو محرك كشف AI جديد.
- ربط كل هدف بمتطلب وحالة استخدام وطريقة تقييم.
- توضيح مساهمات التحصين والقياس وتكامل الشبكة ومساعد التحليل دون ادعاء تفوق غير مقاس.
- تثبيت رؤية الهاتف كبيانات شبكية فقط، وفصل دور AI عن كشف Wazuh واستجاباته المسبقة.
- التمييز بين نطاق مطلوب وتنفيذ مثبت؛ لا تُدرج نتائج نهائية قبل القياس.

### الفصل الثاني: الإطار النظري والدراسات السابقة

- تعريف المفاهيم والتقنيات ذات الصلة فقط، مع مصادر أصلية مناسبة.
- مقارنة الدراسات في الهدف والمنهجية والبيئة والمقاييس والنتائج والقيود، لا الاكتفاء بسرد الأدوات.
- ربط الفجوة البحثية بمساهمات المشروع القابلة للاختبار.
- مراجعة كل مرجع: المؤلف، العنوان، السنة، جهة النشر، DOI/الرابط، والعبارة التي يسندها.
- وجود DOI صحيح لا يثبت أن المرجع يدعم الادعاء المنسوب إليه؛ يلزم فحص المحتوى.
- تمييز الأدوات التي تُناقَش نظرياً عن المكونات المنفّذة فعلاً.

### الفصل الثالث: المنهجية وتصميم النظام

- متطلبات FR/NFR قابلة للتتبع والاختبار، مع أولوية متوافقة مع القرارات المعتمدة.
- معمارية ومخططات DFD وتسلسل وبيانات تتوافق مع التصميم، وتُظهر حدود التنفيذ بوضوح.
- فصل المعمل التاريخي عن بيئة التحقق الأحدث وعن الطوبولوجيا المقترحة.
- توثيق سياسات الاستجابة، وجهة التنفيذ، الموافقة، المهلة والتراجع، وحدود الثقة والمخاطر المتبقية.
- مطابقة أسماء CLI والحقول ومعرّفات القواعد مع الكود، أو وسم الرسم بأنه تسلسل مفاهيمي غير تنفيذي.
- عرض PILOT بخمس محاولات ثم `n≥30` أو أكثر وفق الخطة ونتائج التباين، وbaseline لمدة 12 ساعة لكل نظام/إعداد، باعتبارها خطة لا نتائج منجزة.
- توضيح جمع الطوابع الزمنية والمزامنة والأدلة المستقلة والمحاولات الفاشلة والمستبعدة.
- تخصيص تقييم ملائم لجودة AI؛ لا يُفترض أن قياس زمن كشف Wazuh يثبت جودة الشرح أو الترابط.

ملاحظات ثابتة إضافية: `WazuhAPI` يعطل تحقق TLS افتراضياً؛ `notify` في منفّذ AI يعيد noop ولا يرسل Telegram؛ `quarantine_file` مرفوض يدوياً ويُحال إلى AR؛ `knowledge.tokenize` لا يفهرس الحروف العربية. لا تُعرض هذه الوظائف كضمانات أوسع من الكود. سجل JSONL بإضافة فقط من التطبيق ليس سجلاً محصناً ضد العبث بحد ذاته.

في رسم §3.7.5، الأمران `analyze` و`approve --hash` ليسا واجهة `soc_ai.py` الحالية؛ الواجهة تتضمن `explain/correlate/suggest/respond/report` والموافقة `--approve`. كما أن `LINK_KEYS` هي srcip/file/mac وليست user. ينبغي مطابقة الرسم والشرح أو وسمهما بوضوح كتجريد مفاهيمي.

## 7. التحقق المحلي وحدوده

نتيجة التشغيل في مراجعة 2026-09-30:

- 178 اختباراً ناجحاً، و73 اختباراً فرعياً ناجحاً.
- 28 اختباراً متخطّاة لعدم توفر محرك Wazuh في جلسة المراجعة.
- `validate_all.sh`: النتيجة `ALL CHECKS PASSED`؛ تحقق صيغة ومعرّفات وفحوص أسرار محدودة، لا تدقيق أسرار شامل أو إثبات تشغيل.
- إعادة إنتاج GUIDE-01..06 استخدمت بيانات اصطناعية وLLM/API وهميين؛ لا اتصال خارجي ولا حظر أو حذف فعلي. ليست تجارب أداء SOC ولا نتائج فصل خامس.

إعادة تشغيل مجموعة الاختبارات من جذر المستودع دون pycache أو pytest cache، مع حصر الملفات المؤقتة داخل مساحة العمل:

```bash
TMPDIR="$PWD/.git" PYTHONDONTWRITEBYTECODE=1 python3 -B -m pytest tests -q -p no:cacheprovider
PYTHONDONTWRITEBYTECODE=1 bash scripts/validate/validate_all.sh
```

لا تشمل هذه المراجعة تدقيق كل صورة وصوت ومصدر أصلي، ولا إعادة تحقق خارجي لكل DOI، ولا تشغيل المعمل التاريخي. الاختبارات الحالية لا تتضمن بالضرورة حالات GUIDE-01..06؛ يجب إضافتها عند الإصلاح.

## 9. قائمة قبول النسخة الأكاديمية

هذه بوابات لم تُعلَّم مكتملة بمجرد إنشاء هذا الدليل:

- [ ] اعتماد `midterm/` كنسخة العمل الوحيدة وتوحيد بيانات النطاق والأولويات والإصدارات.
- [ ] إرفاق حالة تحقق ودليل مؤرخ لكل ادعاء تنفيذ مهم، وذكر حدود المحاكاة عند موضع الادعاء.
- [ ] مراجعة روابط الأهداف ← الأسئلة ← المتطلبات ← حالات الاستخدام ← طريقة التقييم.
- [ ] تدقيق مراجع الفصل الثاني ومحتواها واستشهاداتها، لا DOI وحده.
- [ ] تصحيح تعميمات الفصل الثالث وواجهات CLI والمخططات؛ تحديث الصور إذا تغيرت مصادر Mermaid.
- [ ] عرض ضوابط الأمان الحالية وحدودها بصدق؛ لا تسمية تحسين مخطط بأنه منفذ.
- [ ] فصل أهداف NFR وخطة العينات عن نتائج القياس، وتحديد بروتوكول تقييم AI.
- [ ] تأكيد قالب الجامعة ومراجعة DOCX/RTL والفهارس والتسميات بعد التحويل.
- [ ] مراجعة الفريق/المشرف واعتماد النسخة؛ لا تُسمّى المراجعة الذاتية مراجعة مستقلة.

يمكن اعتماد الفصول 1–3 دون إنهاء كل إصلاح برمجي إذا وصفت التصميم والقيود والحالة الفعلية بأمانة. أما الادعاء بأن الضوابط أو النتائج مكتملة فيحتاج أدلتها أولاً. الفصل الرابع يوثّق التنفيذ وأدلته، والخامس يعرض النتائج المقاسة؛ لا تمنع هذه المراحل استكمال المقدمة والنظرية والمنهجية الآن.
