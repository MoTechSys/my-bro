- تشمل الخطة UC-01..08: اختبار نشر/اتصال واحد، وسبع آليات كشف/تكامل. لا تُسمّى جميعها اختبارات كشف هجمات.

FIM: إنشاء/تعديل/حذف، 30 لكل نوع على الأقل. UC-01 خمس دورات اتصال مستقلة، لا معدل كشف. تحفظ جميع المحاولات ولا يستبدل الفشل بالنجاح (ISSUE-051).

## 2. بوابة الجاهزية والسلامة (Preflight)

### G2-0 — أول خطوة: فحص دقّة alert.timestamp (ISSUE-061، سابقاً v3.1 ISSUE-052)

قبل أول PILOT، على المدير الفعلي أو نسخة خام كاملة موثقة منه، افحص طوابع alerts.json **الأصلية** لا Indexer/@timestamp أو JSON مصطنع:

```bash
python3 -B scripts/measure/mttd.py --inspect-alert-timestamps \
  --alerts /path/to/native-alerts-previous.json /path/to/native-alerts-current.json
```

الأمر قراءة فقط ويعيد per-manager عدد خانات الكسور، أمثلة خام مع مراجعها، أخشن quantum ممثل، وجود كسر غير صفري، وhashes. صحح مسارات المثال إلى نسخك المصرح بها، واحفظ النتيجة مع إصدار Wazuh وقياسات NTP وتاريخ الرصد/المراجع. لا تدّعِ ms لمجرد تحويل timestamp إلى integer أو ظهور `.000`؛ عدد الخانات يصف **التمثيل** لا دقة المولد/الساعة. افحص عدة تنبيهات/أحداث بفواصل معلومة، وتحقق من مصدر المولد أو وثيقته على الإصدار الفعلي. `FORMAT_OBSERVED_NATIVE_RESOLUTION_UNVERIFIED` ليست موافقة تلقائية.

دليل الخروج: مراجعة بشرية تحدد native resolution وعدم يقين الساعة ونطاق المدير/الإصدار، وتربطها بالـmanifest/time_refs. إن كان المصدر ثانية، تعامل مع t2/t2_prime/t6 بدقة لا أفضل من ثانية (±1s محافظ عند جهل التقريب)، وقيّد عرض المقاييس المشتقة وفق أضعف طرف؛ إن لم يحسم، تبقى الدقة UNVERIFIED ولا تنشر زمن ms. حدث §5.4 وسجل G2 بالدليل، لا بنتائج الاختبارات المحلية. **هذا الفحص لم ينفذ في المعمل بعد؛ PILOT لا يبدأ قبل مراجعته.**

### بقية بوابة الجاهزية

1. معمل افتراضي مصرح به، لقطة استعادة (Snapshot)، وإمكانية دخول من وحدة تحكم الـVM. لا فحص لشبكة عامة، ولا تنزيل/تشغيل عينات برمجيات خبيثة حقيقية؛ استخدم EICAR أو نص YARA اصطناعياً غير تنفيذي.
2. ثبّت `git commit` ونسخة الإعداد المنشورة وبصمات SHA-256 لملفات القواعد والسكربتات وfeed ونسخ الأدوات. لا تعتبر ملفات المستودع دليلاً على تطبيقها. لا تنشر نسخة `ossec.conf` الخام المحتوية على مفتاح API.
3. راجع [المعمارية](../docs/02_ARCHITECTURE.md) وأعد توثيق الحالة الحية. المرجع التاريخي للوكيلين هو [p04_0.png](../docs/sources/screenshots/wazuh_guide/p04_0.png)، ولـSuricata [p30_0.png](../docs/sources/screenshots/wazuh_guide/p30_0.png). حالة `win1` في اللقطة القديمة disconnected وليست نتيجة للجولة الجديدة. نوع الخادم وإصداره الدقيق والأسماء/الواجهات الحالية تُسجّل من الجهاز، لا تُستنتج من prompt.
4. حدّد مصدر الوقت والمنطقة الزمنية على كل VM والجهاز المولّد للأحداث. سجّل فرق الساعة وعدم يقينه قبل الجولة وبعدها. الطوابع t0..t6 أعداد صحيحة UTC epoch milliseconds، مع `ntp_offset_ms` لكل جهاز = ساعة الجهاز ناقص UTC؛ التصحيح بطرح offset مرة واحدة. أي قيمة مطلقة >100 ms في manifest أو أي محاولة ترفض **الجلسة كلها** آلياً بـ`exclusion_reason=INVALID`، بما فيها محاولات سابقة وجولات أخرى داخل session_id؛ ±100 مقبول. نقص قياس جهاز يمنع قبول العقد، ولا يُفترض صفراً. التنفيذ يحتاط أيضاً عند uncertainty>100؛ سجل ISSUE-057 لهذا التشدد الإضافي.
5. تحقّق من الوكلاء والخدمات وبدء مراقبة FIM بعد المسح الأولي. افحص القواعد المنشورة باستخدام `wazuh-analysisd -t`. استبدل placeholders في نسخة المعمل؛ نجاح فاحص المستودع الذي يحيدها لا يثبت صلاحية النسخة الخام للنشر.
6. افحص حقول عينة JSON فعلية لكل UC قبل القياس، وكذلك مسار السجل وصلاحية القراءة وتدويره والحد الأدنى للتنبيه. لا تغيّر الإعداد في منتصف الجولة. استخدم `wazuh-logtest` لفحص فك الترميز والقواعد عند ملاءمته؛ ناتجه ليس تنبيهاً حياً ولا يقيس الشبكة أو AR [R1، R2].
7. قبل UC-03 راجع توجيه AR لكل نظام وسلامة سكربت الحذف؛ قبل #14 كان التوجيه مزدوجاً؛ الحالي استجابة local واحدة باسم remove-threat.exe مع ملف native مناسب لكل OS وhelper على Linux. المراجعة المستقلة في #17؛ الاعتماد الأصلي ما زال مطلوباً. الحذف لا يُسمح به إلا لملفات الاختبار في VM معزولة وبعد مراجعة مختصة؛ عند غيابها الحالة `BLOCKED` والسبب `SAFETY_REVIEW_REQUIRED`.
8. لا تُعطّل Defender كخطوة افتراضية. إذا سبق Wazuh إلى حجر EICAR فاحفظ دليله وصنّف التداخل `INTERFERED`، ولا تنسب الحذف إلى Wazuh. أي استثناء أمني يحتاج موافقة وتوثيقاً مستقلاً وإعادة الحماية بعده.

أوامر تحقق قراءة فقط، تُشغَّل على **الجهاز المحدد** لا على حاسوب المحلل عشوائياً:

```bash
# Wazuh manager (administrative shell)
sudo /var/ossec/bin/wazuh-control info
sudo /var/ossec/bin/agent_control -l
sudo /var/ossec/bin/wazuh-analysisd -t
date -u '+%Y-%m-%dT%H:%M:%S.%NZ'
# Kali endpoint (separate terminal on Kali)
cat /etc/os-release
systemctl is-active wazuh-agent
getent group wazuh
id
cat /proc/self/loginuid
```

```powershell
# Windows endpoint: administrative Windows PowerShell
Get-Service -Name Wazuh
[DateTimeOffset]::UtcNow.ToString('o')
w32tm /query /status
```

`date` و`w32tm /query /status` يوثقان الوقت/المزامنة ولا يثبتان وحدهما حد 100 ms. استخدم قياسات offset من خدمة الوقت الفعلية؛ لا تفترض وجود chrony أو systemd-timesyncd على كل صورة.

## 3. التسجيل والربط (Ground Truth and Correlation)

### 3.1 سجل المحاولات

أنشئ JSONL خارج المجلدات المراقبة، كائناً واحداً لكل محاولة، مع manifest `version=2`. لا يقبل العقد الجديد `status=READY/DETECTED` من المشغّل؛ التصنيف يحسب من الدليل. تفاصيل الحقول وأمثلة التشغيل في [README](README.md).

| الحقل | المعنى والقيود |
|---|---|
| `schema_version=2`, `session_id`, `run_id`, `trial_id`, `uc`, `variant` | session تضم جميع أجهزتها وجولاتها؛ الهوية الفريدة run+trial؛ UC-01..13 معرفات لا إثبات تنفيذ |
| `phase` | PILOT / MEASURED / BASELINE / SUPPRESSION_CONTROL؛ تلخيص منفصل لكل مرحلة |
| `exclusion_reason` | null أو BLOCKED / INVALID / INTERFERED / AMBIGUOUS؛ للاستبعاد `reason` تفصيلي؛ لا حذف للصفوف |
| `t0..t6`, `t2_prime` | **سبعة** طوابع t0..t6 رغم عبارة «ستة» في المصدر (ISSUE-050)، وVT إضافي. كل حقل حاضر: integer epoch ms أو null |
| `time_refs`, `missing_reasons` | مرجع لكل طابع غير null وسبب لكل مفقود؛ لا اختلاق طابع من ترتيب السطور أو mtime |
| `ntp_offset_ms` | خريطة كاملة لكل أجهزة session، لا فرق مصدر/مدير واحد كما في v1؛ القياسات الخام/مراجع chrony أو w32tm قبل/بعد وخلال الجلسة تحفظ للمراجعة |
| `event_valid`, `source_ref` | إثبات مستقل للحدث الإيجابي؛ غياب تنبيه ليس غياب الحدث. مصدر الحساس قد يفشل: يلزم عندئذ مراقب فعل مستقل |
| `expected_rule_ids`, `expected_levels`, `target_key` | التنبيه النهائي للكشف، محدد مسبقاً؛ ليس بالضرورة تنبيه مرحلة t2 |
| `stage_selectors` | t2 وt2_prime وt6: لكل منها rule_ids/levels/target_key؛ ربط خام مستقل. t6 غير null يستلزم selector تأكيد؛ لا مجرد إقرار |
| `window_start`, `match_start`, `observe_until`, `window_s`, `window_ref` | نوافذ ISO8601 على مقياس ساعة المدير؛ UC-04 يميز بداية المسح عن مرساة الموعد عند نهايته؛ تغطية معلنة ثابتة |
| `poll_interval_ms=1000`, `completion_kind` | t3 رصد أول ظهور عبر API كل ثانية؛ t5 غير null يتطلب independent_observation |
| `source_precision_ms`, `timestamp_precision_ms`, مراجع الأدلة | دقة المصدر الفعلية وعدم يقين المراقب؛ تحويل الثواني إلى ms لا يمنح دقة ms |

manifest لكل run يحوي هوية الوكيل/المدير/OS، commit كامل وSHA256 للإعداد المنشور، timing_definition وlatency_kind، coverage_start/end/ref، session_id، devices={device:{ntp_offset_ms,uncertainty_ms,clock_ref}}، وclock_map لجميع الطوابع بما فيها t2_prime. طوابع المدير الثلاثة تستخدم الجهاز نفسه. تغيير التعريف/القواعد/المستويات/نوافذ القياس أو stage protocol يحتاج run جديدة. لا تقبل hashes/مراجع الإقرار وحدها كإثبات نشر أو مزامنة فعلية.

### 3.2 قواعد الربط

- FIM/VT/YARA: معرف الوكيل + المسار الفريد للمحاولة + نوع الحدث/المرحلة؛ البصمة وحدها لا تكفي لأن عشر نسخ EICAR تحمل البصمة نفسها. تحقّق من المسار كما ورد فعلياً في JSON: `syscheck.path` أو `data.virustotal.source.file` أو `data.yara_scanned_file`.
- auditd: معرف الوكيل + audit serial + PID/AUID/الأمر ونافذة المحاولة؛ لا تستخدم `100210` وحدها لأن `sudo` أيضاً red في القائمة الحالية.
- HTTP: علامة `trial_id` في URL، مع عنواني المصدر والوجهة ووقت سجل Apache. تأكّد في PILOT من حفظ العلامة بعد فك الترميز.
- Suricata: زوج IP/المنافذ + نافذة المسح + `flow_id` و`signature_id` عند توفرهما؛ لا يكفي تنبيه 86601 لا علاقة له بالمسح.
- العمليات: الوكيل + PID + المنفذ في سطر عملية `nc` الفعلية + نافذة المحاولة. لا يكفي وجود العبارة في سطر shell أو أداة اختبار.
- عند تكرار التنبيهات اختر أول تنبيه نهائي مطابق، واحفظ عدد البقية. إزالة تكرار السجل تكون بمفتاح `(manager_name, alert_id)`، مع مرجع السطر. `rule.firedtimes` ليس عدد محاولات التجربة.
- لا تستنتج ترتيباً سببياً من ترتيب وصول السطور فقط. عند تعذر الربط أو التباس عدة أحداث، سجّل `AMBIGUOUS` ولا تختَر الأقرب زمنياً تلقائياً.

### 3.3 ملف الأدلة

المصدر الأساسي للتنبيه هو `/var/ossec/logs/alerts/alerts.json` على المدير [R1]. احفظ نافذة الجولة والسجلات المدورة التي تغطيها، لا تعتمد على `tail` بعد انتهاء التجربة. احفظ سجلات المصدر وAR على الجهاز، ولقطات الشاشة المكمّلة، وmanifest للإعداد والوقت، وبصمات الأدلة. لا تمسح سجلات النظام لإعادة ضبط التجربة.

مجلد التسليم المقترح عند توفر أدلة منقّحة: `docs/lab/evidence/UC-XX/<run_id>/`. هذا مسار مستقبلي، وليس ادعاءً بوجود أدلة جديدة. احفظ الخام الحساس في مساحة خاصة مع صلاحيات مقيدة؛ انشر نسخة منقحة بلا أسرار أو محتوى ملفات شخصية. وثّق التنقيح حتى لا تُفقد مفاتيح الربط.

### 3.4 المشغّل وجمع الأدلة

`scripts/measure/trial_runner.sh` يستدعي backend Python stdlib في وضع معزول. `--lab` إلزامي لأي أمر، و`--replay` يجمع أدلة مسجلة ولا يسمح بأمر إطلاق. لا SSH تلقائي ولا نشر مراقبين ولا تعطيل حماية. راجع واجهة spec/manifest/observer والأمثلة في README قبل التشغيل.

- يسجل t0 ويحفظ launch intent في `<output>.pending` مع fsync **قبل** إطلاق argv المحدد دون shell/eval، ثم ينتظر نافذة الرصد ويجمع الأدلة ويضيف سطر JSONL واحداً. مهلة الطفل محدودة، وتنظف مجموعة عملياته؛ لا تستخدمه لأمر ينشئ خدمة يفترض استمرارها بعد انتهائه.
- يجمع t1 من JSON/EVE بحقول exact، أو audit serial+PID، أو Apache client IP+URI كامل بعلامة المحاولة. لا adapter عام يختلق وقت FIM من mtime؛ FIM دون مصدر مؤرخ مستقل يظل null. serial/PID غالباً لا يعرفان قبل الإطلاق؛ يلزم مراقب مستقل أو replay بعد استخراجهما من دليل، لا تخمين.
- يجمع t2/t2_prime/t6 من ملفات alerts.json المدورة المحددة صراحة، مع الهوية والقاعدة والمستوى والمفتاح والنافذة. يجمع t3/t4/t5 من JSONL مراقب خارجي مدقق: أول ظهور فعلي لتنبيه t2، بداية endpoint، واكتمال مستقل. **المشغّل لا يثبّت ولا ينفّذ مراقب Indexer/inotify/iptables بنفسه**. غياب المراقب ليس وقتاً صفرياً.
- `--wait` يغطي window_s ولا يقصر إذا ظهر تنبيه مبكراً؛ outcome exit/timeout لا يقرر صحة الحدث. دليل action_confirmed مستقل يبقي محاولة فشل الحساس MISSED؛ إن لم يمكن إثبات الحدث فالصف INVALID لا نجاحاً مفترضاً.
- يتطلب مجلداً خاصاً موثوقاً خارج FIM؛ قفل journal يمنع كاتبين متزامنين لنفس الملف. يمنع symlink/hardlink للخرج وإعادة trial_id. لا يحمي من تعديل دليل داخل مجلد يسيطر عليه مهاجم.
- فشل الجمع يحفظ محاولة INVALID وسببه. تعطل قسري قد يترك pending أو سطراً جزئياً؛ يمنع الاستئناف حتى المراجعة، **لا تمسحه ولا تعِد الهجمة بنفس الهوية**. احتفظ به ضمن مقام المحاولات وصحح الاستيراد مع سجل تدقيق.
- hashes تثبت البايتات المقروءة لا أصلها أو اكتمال التدوير. وفر صادرات كاملة/متسقة وبصلاحيات مقيدة؛ الملف الناقص أو السطر الجزئي خطأ صريح. لا تمرر أسراراً في argv لأنها تحفظ في سجل المحاولة.
- بعد انتهاء session أعد `mttd.py` على **كل** محاولاتها وكل سجلاتها: أي spike ساعة يرفض جميع الصفوف في التقرير، دون إعادة كتابة journal الخام. لا تعتمد تقرير محاولة منفردة قبل إغلاق الجلسة وفحص قياسات نهايتها.

## 4. تعريف المقاييس والإحصاء — v3 §5

`t0` إطلاق الفعل؛ `t1` وقت الحدث من المصدر؛ `t2` timestamp لتنبيه المدير؛ `t3` أول ظهور مرصود في Indexer/Dashboard؛ `t4` بداية الاستجابة على endpoint؛ `t5` اكتمال مستقل؛ `t6` timestamp لتأكيد المدير. لا تستخدم `@timestamp` بدل وقت الظهور، ولا نجاح السكربت بدل اكتمال الفعل. التخزين UTC ms على ساعة كل جهاز؛ الحساب بعد طرح offset، والخرج **بالثواني**.

| المقياس | الصيغة الحرفية بعد تصحيح الساعات |
|---|---|
| D_source | t1 − t0 |
| MTTD | t2 − t1 |
| MTTD_e2e | t2 − t0 |
| L_vis | t3 − t2 |
| L_AR_trigger | t4 − t2 |
| L_AR_complete | t5 − t4 |
| L_AR_e2e | t5 − t0 |
| L_confirm | t6 − t5 |

هذه **ثمانية أسماء بالضبط**؛ لـUC-03 يضاف **D_VT=t2_prime−t2** منفصلاً. t2 لـUC-03 هو FIM 100200/100201، وt2_prime هو VT 87105؛ لا يستبدل أحدهما بالآخر. بذلك L_AR_trigger الحرفي يشمل تأخير VT؛ لا تسوّقه كقياس نقل manager→execd وحده (ISSUE-053). UC-07: selector t2 محفز FIM وfinal detection هو 108001، ولا تخلط تأكيد الفحص ببدايته. MTTD لـSuricata يسمى كما في §5.2 لكن مع وصفه **تأخير تكامل eve→manager** لا كامل زمن كشف الهجوم.

قيمة مفقودة تعطي null/MISSING_TIMESTAMP؛ فرق سالب يعطي null/INVALID_ORDER ولا يقص إلى صفر؛ كل مقاييس محاولة مستبعدة null/EXCLUDED. ملخصات الزمن شرطية على DETECTED ذي المقياس الصالح: انشر n لكل مقياس وأعداد المفقود/المستبعد/MISSED، ولا تفسرها كزمن جميع المحاولات. UC-01 لا يحتسب كمعدل كشف؛ الاتصال المتخصص ما زال غير منفذ.

### 4.1 المقامات وفواصل الثقة

- `detection_rate_all_attempts` = DETECTED / جميع محاولات المجموعة، **بما فيها الاستبعادات** وفق v3. `wilson_95_all_attempts` فاصل Wilson 95% بالمقام نفسه.
- `detection_rate_valid` = DETECTED/(DETECTED+MISSED)، و`wilson_95_valid` للمقام الشرطي القديم المسمى بوضوح (ISSUE-052). لا يعرض دون معدل جميع المحاولات وأسباب الاستبعاد.
- مجموعات مستقلة run/UC/variant/phase؛ لا تجميع تلقائي بين OS/config أو PILOT وMEASURED وSUPPRESSION_CONTROL. المتأخر MISSED ضمن الموعد؛ لا يستبدل المحاولة.
- Wilson ثنائي 95% يستخدم z=1.959963984540054؛ n=0 يعطي null، لا 0%. الاستقلال وتجانس احتمالات المحاولات افتراضات تحتاج مراجعة التصميم؛ الفاصل ليس ضمان تعميم.

### 4.2 ملخص الزمن وحجم العينة

لكل مقياس: n، median، Q1، Q3، IQR=Q3−Q1، P95، min/max، mean وsample SD (null إذا n<2). quantiles بطريقة **type 7 linear interpolation**: h=(n−1)q. لا عينات = null لا صفر. L_vis دقته تقيدها فترة polling=1000 ms إضافة إلى الساعة، وبقية العرض لا يتجاوز أضعف دقة مصدر.

`sample_size(sigma_hat, margin=1.0) = max(30, ceil((1.96*sigma_hat/margin)**2))`، sigma وmargin بالثواني؛ sigma غير سالب وmargin موجب. بعد خمس عينات PILOT صالحة لكل مقياس، يؤخذ الأكبر بين الناتج والحد الأدنى30 لكل UC وفق v3.1 §9 A2. ثبت `planned_n` قبل MEASURED؛ لا انتقاء حجم العينة بعد p-value. هذه صيغة تخطيط متوسط على أساس SD مقدر وليست ضمان دقة P95 أو قدرة MWU؛ خمس عينات قد تكون غير مستقرة.

### 4.3 FP/h وH4

- FP/h = تنبيهات التهديد المحكوم بكذبها / ساعات النشاط الطبيعي. FIM لتعديل مشروع مطابق صحيح لسياسة التغيير، وقد تكون مطابقة red صحيحة مع إنذار تهديد كاذب؛ لا تخلط القياسين. FPR=FP/(FP+TN) خارج هذا الحساب دون تعريف TN وتجارب سالبة معدودة.
- Poisson **one-sided exact upper 95%**: عند k=0، −ln(.05)/hours؛ عند k>0، عكس CDF للعدد عددياً في log-space وبحث ثنائي، مكافئ chi-square(2(k+1),.95)/(2×hours)، بلا تقريب طبيعي. 0/12h يعطي upper≈0.2496؛ 1/12h≈0.3953. الهدف H3 upper<0.5؛ للمقارنة التاريخية 1/6h≈0.7906 فلا يحقق الهدف. يفترض عملية عد Poisson؛ clustering/تغير معدل النشاط يحد الاستنتاج.
- BASELINE له start_ms/end_ms على مقياس المدير، activity_ref، وadjudications لكل manager_name/alert_id مع is_false_threat_alert=true/false/null وreason/ref. baseline_rule_ids نطاق معلن لكل run، ومجالات نصف مفتوحة [start,end). يحسب اتحاد التعرض؛ إذا بقي تنبيه بلا حكم فـfp_upper_95=null، ويعرض unresolved والحد المحافظ إذا اعتبرت كلها كاذبة. أقل من12h تحذير لا اكتمال baseline.
- H4 يستخدم **L_AR_complete** ومجموعتين مستقلتين hardened/official بنفس OS/timing_definition وUC/variant ومرحلة MEASURED، مع design_ref للتخصيص العشوائي/الظروف المتكافئة. لا يشغّل المحلل السكربت الرسمي غير الآمن.
- Mann–Whitney U أحادي **greater**: hardened يميل إلى زمن أكبر، α=.05. midranks للتعادل؛ exact inclusive permutation إذا combinations≤100000، وإلا تقريب طبيعي مع تصحيح ties وcontinuity. يعرض U وp والطريقة وحجمي العينتين وΔmedian.
- **p غير دالة لا تثبت H4 أو non-inferiority بحد ثانية**؛ ولا تكفي Δmedian المرصودة وحدها لإثبات حد سكاني. claim قدرة n=30 في الخطة غير مثبتة بـplan_math؛ ISSUE-054 ما زال OPEN للمراجعة المنهجية. النتيجة CALCULATED_NOT_H4_PROOF، لا قرار نجاح آلي.

### UC-01 — نشر الوكلاء والتحقق من الاتصال

### UC-03 — VirusTotal والاستجابة بحذف ملف الاختبار

2. نفّذ 30 عملية مسح على الأقل منفصلة بالإعداد نفسه، مع حفظ مخرجات nmap ووقتَي البداية والنهاية والمصدر والهدف والمنافذ. السكربت الموجود `nmap_scan.sh` يفحص المنافذ الافتراضية؛ لا تشغله دون مراجعة النطاق، ولا تخلط جولات ذات نطاقات مختلفة.
3. اربط تنبيه eve بالتنبيه النهائي في المدير (المتوقع في هذا المشروع 86601، وافحص المستوى المنشور في PILOT) بواسطة signature/flow/العناوين والنافذة. انتظر 120 s بعد نهاية المسح؛ لا تُعِد المسح قبل انتهاء فترة الكبت المحددة في التوقيع.
4. سجّل طبقتين منفصلتين: هل ولّدت الحركةُ حدث Suricata المتوقع؟ وهل وصل هذا الحدث إلى Wazuh؟ حدث Suricata موجود بلا تنبيه Wazuh = فشل تكامل؛ حركة اختبار مثبتة تستوفي التوقيع بلا حدث Suricata = فشل كشف حسّاس، لا محاولات مستبعدة.

**القياس:** MTTD=t2−t1 هنا **تأخير تكامل Suricata→Wazuh** وفق تعريف v3، لا MTTD من بدء الهجوم (ISSUE-053). زمن بدء المسح→التنبيه قياس نهاية إلى نهاية مستقل، لأن إصدار توقيع المسح قد يتطلب عدة حزم. **السالب:** طلب HTTP عادي إلى خدمة المعمل دون مسح؛ راجع أي تنبيه بدلاً من افتراض غيابه. **التنظيف:** أوقف مولّد المسح، ولا تحذف eve.json أو تغيّر القواعد.

### UC-05 — auditd وقائمة الأوامر المصنّفة

المرجع: [دليل auditd](../docs/lab/UC-05_auditd_malicious_commands.md)، و`suspicious-programs`، و[R7].

**المتطلبات:** auditd عامل، قواعد execve محملة، AUID جلسة المستخدم يطابق 1000 وفق الإعداد، وشرط المجموعة موثق (ISSUE-031). قيمة UID الفعلية لا تكفي لإثبات AUID. تحقق من الاسم المفكوك `data.audit.command`، فقد يختلف عن الاسم في سطر الأوامر أو هدف symlink.

1. افحص `sudo auditctl -l` والـloginuid و`command -v nc` في مرحلة الجاهزية، لا في وسط المحاولة. افصل أحداث sudo الناتجة عن التجهيز لأنها red أيضاً.
2. نفّذ `nc -h` مرة واحدة من جلسة المستخدم المطلوبة، بلا فتح اتصال أو مستمع، واحفظ توقيت البداية والنهاية وحالة الخروج. بعض نسخ nc تعيد خروجاً غير صفري للمساعدة؛ المعيار هو إثبات execve لا رقم الخروج وحده.
3. استخرج سجل الحدث من `/var/log/audit/audit.log` واربط سجلات SYSCALL/EXECVE ذات audit serial نفسه مع PID/AUID/الأمر. ابحث عن 100210 L12 خلال 120 s وأعد ذلك 30 مرة منفصلة على الأقل.
4. إذا كان nc لا يطابق اسم القائمة، سجّل عدم التطابق قبل القياس كعائق إعداد؛ لا توسّع القائمة سراً. لا تستخدم `netcat_tests.sh` لهذه التجربة لأنه يضيف اختبار مستمع UC-08 أيضاً.

**السالب:** عشر عمليات `whoami` (yellow في القائمة الحالية)؛ لا يُنتظر لها 100210، مع السماح بسجلات audit الطبيعية. **القياس:** timestamp داخل audit serial→تنبيه 100210 بعد التحقق من المنطقة الزمنية/الدقة؛ لا تنسب تنبيه sudo المجاور إلى nc. **الحد العلمي:** هذا اختبار مطابقة سياسة أسماء أدوات، وليس إثبات أن كل استعمال nc هجوم. **التنظيف:** لا توجد عملية مستمعة ولا ملفات تهديد؛ احتفظ بالسجلات.

### UC-06 — كشف نمط Shellshock دون استغلال فعلي

المرجع: [دليل Shellshock](../docs/lab/UC-06_shellshock.md). **المتطلبات:** خدمة Apache في المعمل ومسار HTTP ثابت **غير CGI**، وصول User-Agent إلى access.log وتكامل السجل مع Wazuh. لا تفعّل ثغرة أو CGI ولا تعدّل الجدار الناري لمجرد الاختبار.

1. نفّذ PILOT بطلب واحد إلى المسار الثابت لتأكيد تسجيل الترويسة وفك الترميز إلى 31168. الطلب أدناه يحتوي نمط اختبار وتعليمة echo فقط، دون قراءة ملفات النظام؛ `LAB_TARGET` عنوان مُتحقق ومصرّح به وليس عنواناً مفترضاً.

```bash
# Approved isolated lab only; target root must be a verified non-CGI resource
: "${LAB_TARGET:?Set the authorized lab host}"
: "${TRIAL_ID:?Set a unique ASCII trial identifier}"
curl --noproxy '*' --max-time 10 --silent --show-error \
  -A '() { :; }; /bin/echo SOC_SHELLSHOCK_TEST' \
  "http://${LAB_TARGET}/?soc_trial=${TRIAL_ID}"
```

2. لكل من 30 محاولة على الأقل، سجّل وقتَي الطلب ومخرجه وحالته، ثم السطر الخام من `/var/log/apache2/access.log` وفيه علامة المحاولة. انتظر 31168 L15 خلال 120 s واربط بالوكيل والطلب نفسه.
3. إذا انتهى curl بمهلة فقد يكون الطلب وصل: القرار مبني على سجل المصدر، لا خروج curl وحده. صفحة Apache العادية لا تعني فشل الكشف أو نجاح استغلال. لا يُدّعى تنفيذ أوامر عن بُعد.

**السالب:** عشر طلبات للمسار نفسه بعلامات مستقلة وUser-Agent عادي؛ لا يُتوقع 31168. **القياس:** وقت سجل Apache بدقة المصدر (قد تكون ثانية)→التنبيه؛ اعرض مجال الفعل إن احتجت قياساً بدقة أعلى ولا تزعم دقة مللي ثانية من سجل ثوانٍ. **التنظيف:** لا ملفات أنشأها الهدف؛ احفظ سجلات الجولة ولا تمسح access.log.

### UC-07 — سلسلة FIM → فحص YARA → تأكيد النتيجة

المرجع: [دليل YARA](../docs/lab/UC-07_yara.md)، و`40-active-response-yara.xml`، و[R5]. **المتطلبات:** قواعد YARA دائمة المسار، binary قابل للتنفيذ من حساب AR، الملف داخل المجلد الصحيح، ونتائج AR تُجمع فعلياً. Windows مشروط بإثبات التشغيل وليس نجاح النسخة Linux.

1. فضّل **ملف اختبار نصياً سليماً** وقاعدة اختبار واضحة على تنزيل عينات حقيقية. المحتوى الإيجابي المقترح `SOC_T10_YARA_POSITIVE`، والسالب `SOC_T10_YARA_NEGATIVE`. ملف الإعداد الاصطناعي أدناه يحتاج موافقة ونشراً في نسخة قواعد اختبار في المعمل قبل PILOT؛ ليس جزءاً مضافاً فعلياً إلى `wazuh/`، ولا قاعدة Wazuh برقم جديد.

```yara
rule SOC_T10_TestMarker
{
    strings:
        $marker = "SOC_T10_YARA_POSITIVE"
    condition:
        $marker
}
```

2. سجّل ملف الاختبار وقاعدته وبصمتهما، وتحقق بفحص YARA مباشر خارج المجلد المراقب أن الإيجابي يعطي `SOC_T10_TestMarker` والسالب لا يعطيها. استخدم الملف نفسه في AR ضمن **ملف إعداد اختباري مُعلن**، ولا تستبدل قواعد الإنتاج دون موافقة/نسخة احتياطية. إذا لم يُعتمد هذا الإعداد فالفرع الاصطناعي BLOCKED؛ يمكن اعتماد EICAR مع feed الحالي فقط بعد إثبات أنه يطابق قاعدة فيه.
3. أنشئ ملفاً إيجابياً فريداً في مجلد YARA المراقب، واحفظ وقت الكتابة. انتظر 100301 L7 على Linux (أو 100304 على Windows المعتمد) ثم 108001 L12 باسم القاعدة ومسار الملف نفسيهما. كرّر 30 مرة على الأقل.
4. لفرع التعديل، أنشئ ملفاً سالباً وانتظر دخوله إلى FIM؛ أضف العلامة الإيجابية ثم انتظر 100300 L7 (أو 100303 على Windows) وتأكيد 108001. 30 محاولة مستقلة على الأقل، غير مدمجة مع فرع الإضافة.
5. احفظ سطر نتيجة YARA على الجهاز وتنبيه المدير. الملف يُفترض أن يبقى؛ الفحص ليس حذفاً. سجل YARA الحالي قد لا يتضمن زمناً دقيقاً للإنجاز؛ استخدم تأخير تأكيد AR من تنبيه FIM إلى 108001، والزمن الفعلي `null` ما لم يوجد مصدر توقيت موثوق.

**السالب:** عشر ملفات دون العلامة الإيجابية؛ لا يُنتظر اسم قاعدة الاختبار. غياب 108001 لا يثبت أن الفحص السالب نُفِّذ بنجاح؛ يلزم دليل تشغيل/خروج، وإلا قيّد الاستنتاج إلى «لا تنبيه مطابق مرصود». **القياس العلمي:** تطابق قاعدة صناعية يقيس صحة خط الأنابيب، لا دقة كشف البرمجيات الخبيثة أو جودة feed. الاختبار بقواعد VALHALLA يسجل منفصلاً مع البصمة والنسخة المحدودة (ISSUE-025). **التنظيف:** ملفات الجولة فقط، وإعادة قواعد ما قبل الاختبار بعد انتهاء جميع محاولات الملف الاختباري مع توثيق الاستعادة.

### UC-08 — مراقبة مستمع Netcat والكبت

المرجع: [دليل مراقبة العمليات](../docs/lab/UC-08_process_monitoring_netcat.md)، و`50-command-process-list.xml`، و`local_rules.xml`، و[R3، R6].

**المتطلبات:** جمع القائمة كل 30 s بحسب الإعداد المنشور، والقاعدة 100051 L7 ذات `ignore=900`. المعنى الرسمي: تجاهل **القاعدة** بعد إطلاقها؛ لا يُفترض أن تغيير PID يتجاوز الكبت. لا تغيّر ignore أو تعِد تشغيل المدير لتسريع الاختبار.

1. تحقق من نوع nc ودعمه للخيارات في PILOT، واختر منفذاً غير مستخدم داخل VM معزولة. من طرفية تفاعلية على الجهاز شغّل مستمعاً بلا `-e` وبلا shell بعيد؛ مثال `nc -l -p "$TEST_PORT"` بعد تعيين المنفذ المعتمد. لا تستخدم غلاف `bash -c` أو timeout يتضمن العبارة نفسها ويخلق تطابقاً مضللاً في قائمة العمليات.
2. من طرفية أخرى، تحقق من وجود socket مستمع وPID بواسطة `ss -lntp` (بصلاحية تسمح بعرض العملية) و`ps -e -o pid,uname,command`؛ احفظ سطر nc الفعلي ووقت أول تحقق. عبارة في سطر wrapper ليست دليلاً على مستمع.
3. أبق العملية 90 s، انتظر تنبيه 100051 حتى 120 s من بدء الفعل، ثم أوقف العملية المحددة بـCtrl-C أو PID موثق؛ لا تستخدم `pkill nc`. سجل 100210 من auditd إن ظهر كحدث جانبي، لا كنجاح UC-08.
4. قبل **كل** محاولة مقاسة، بما فيها الأولى بعد PILOT، انتظر 930 s على الأقل من أحدث تنبيه 100051 على المدير وتحقق من عدم إطلاقها مجدداً في هذه الفترة. الحد = 900 s للكبت + 30 s احتياط البروتوكول؛ راقب بقية الأجهزة حتى لا تلوّث النافذة. كرّر 30 محاولة على الأقل. تتطلب الجولة نحو7.75 ساعات تخطيطية مع الكبت؛ الجدولة المتداخلة تبقى ISSUE-062، ولا يجوز إضعاف930s أو تشغيل أنشطة تؤثر على الكبت/قياس الجولة؛ وثّق هذا بدلاً من ضغط التجارب داخل الكبت.
5. نفّذ تجربة إضافية واحدة منفصلة `SUPPRESSION_CONTROL`: مستمع جديد بعد تنبيه ناجح وقبل انقضاء 900 s مع إثبات وجوده في القائمة. راقب الكبت وسجّله كخاصية تشغيلية، لا تضع غياب التنبيه في مقام المحاولات المستقلة. إذا وُلّد الحدث عرضاً داخل الكبت في الجولة الرئيسية، سجّل خرق البروتوكول ولا تُخفه.

**السالب:** عمليات عادية دون مستمع nc أثناء baseline؛ تطابق القاعدة لنص في سطر عملية غير مستمعة يراجعه المحلل كإنذار كاذب. **القياس:** وقت بدء العملية/مجال الفعل→التنبيه، ويشمل انتظار دورة الجمع؛ لا تتوقع تأخيراً صفرياً أو 30 s كحد مضمون. **التنظيف:** إيقاف مستمع الاختبار والتحقق من إغلاق منفذه.

## 7. النشاط الطبيعي وجدول التقرير

### 7.1 12 ساعة مرجعية على الأقل لكل OS/ملف إعداد

سجّل بداية كل فترة ونهايتها وتوقفات الجمع وأفعال المستخدم، دون اختبارات موجبة خلالها. الجدول دورة نشاط لمدة ساعة تكرر/توزع على 12 ساعة مع توثيق النشاط الفعلي، لا تكرار وهمي لفترة واحدة في حساب التعرض:

| الفترة المقترحة | النشاط المصرح به |
|---|---|
| 0–15 دقيقة | الجهاز خامل مع خدماته المعتادة؛ تحقق أن جمع السجلات مستمر |
| 15–30 دقيقة | إنشاء/قراءة/تعديل مستندات نصية عادية في مسارات الاختبار الموافق عليها |
| 30–45 دقيقة | طلبات HTTP عادية إلى خادم المعمل وعمليات whoami؛ لا مسح منافذ |
| 45–60 دقيقة | إدارة عادية معتمدة؛ إن استُخدم sudo أو nc للمساعدة فسجّل القصد وميّز مطابقة red عن إنذار تهديد صحيح |

على Windows استخدم المكافئ المتاح للأعمال المكتبية، وسجّل البرنامج/الأمر الفعلي بدل افتراض وجود sudo أو nc. مدة تعرض الجهاز لا تصبح ثماني ساعات لأن ثماني آليات تراقبه. عند تغيير إعداد YARA إلى ملف صناعي، الساعة الناتجة تخص ذلك الملف لا feed الإنتاج. إذا انقطع الجمع، أعلن مدة الرصد الفعلية وأكمل التعرض الموثق إلى 12 ساعة؛ لا تحسب الانقطاع زمناً سليماً بلا FP.

كل تنبيه خلال الساعة يراجعه محلل بشري مع سجل النشاط: `EXPECTED_CHANGE` / `POLICY_MATCH_BENIGN` / `FALSE_THREAT_ALERT` / `UNEXPLAINED`. احفظ أيضاً `policy_match` و`is_false_threat_alert` كحقلين مستقلين: قد تكون مطابقة السياسة صحيحة مع إنذار تهديد كاذب. بسط FP/hour هو التنبيهات المحسوم فيها `is_false_threat_alert=true` دون عد مزدوج، أما غير المحسوم فيبقى منفصلاً. لا تُصنِّف تنبيهاً غير مفسر كاذباً لمجرد أن التجربة تسمى baseline؛ أوقف النشاط عند الاشتباه بحادثة فعلية. انشر عدد غير المحسوم منفصلاً. لا تعد الآثار المكررة للحدث محاولات مستقلة؛ اعرض معدل التنبيهات الخام والعدد بعد التجميع بتعريف واضح.

### 7.3 معايير قبول T-10 وتسليم T-11

- T-10 مكتملة **توثيقياً** عندما تغطي UCs الثمانية: المتطلبات، الأفعال، الربط، المتوقع، النوافذ، الضبط، السلامة والتنظيف؛ ومعها تعريف المقاييس والحقول والتمييز بين NOT_RUN والنتائج.
- قبول النظام في المعمل قرار لاحق: خطة كاملة لا تعني أن كل UC جاهزة أو نجحت. لا تُغلق ISSUE-019 ولا تُفتح T-23 على أساس نتائج متخيلة.
- T-11 يحتاج **سجل المحاولات + السجلات الخام + alerts.json + manifest الوقت/الإعداد**؛ alerts.json وحده لا يحصي المحاولات التي لم تُكتشف ولا يضمن وجود وقت المصدر أو وقت AR.
- اختبارات أداة T-11 المقترحة: بيانات اصطناعية معلّمة بوضوح تغطي offsets/timezones، قيماً مفقودة، توقيتاً سالباً، JSON تالفاً، تدوير السجل، تكرار معرفات عبر مديرين، محاولتين بالبصمة نفسها ومسارين مختلفين، MISSED/LATE، وكبت Netcat؛ ليست هذه نتائج المعمل.
- التنفيذ التالي: اعتماد الجاهزية/السلامة وملف YARA الاختباري، تنفيذ PILOT n=5 ثم الجولات وbaseline≥12h على الأجهزة، مراجعة بشرية للأدلة، ثم إنتاج الجدول والرسم للفصل الخامس. PR #24 ينفذ مرشح T-11 محلياً؛ لا تغيير لسكربتات T-15 ولا إغلاق T-11 قبل PILOT معملية ومراجعة مستقلة.
