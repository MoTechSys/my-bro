# خطة الاختبار المُقاس (Measured Test Plan) — T-10

> المالك: [ASTRA] · التاريخ: 2026-09-09 · الحالة: خطة مكتملة توثيقياً؛ التنفيذ والنتائج يحتاجان المعمل.
> هذه وثيقة إجراءات وليست نتائج تنفيذ. لم تُنفَّذ اختبارات المعمل في جلسة إعدادها. يبقى ISSUE-019 مفتوحاً حتى جمع النتائج ومراجعتها.
> المرجع الحاكم: [النية الموحَّدة](../docs/05_PROJECT_INTENT_UNIFIED_VISION.md)، خاصة §5 و§6. لا AI أو TheHive أو Zeek أو Kibana ضمن المنفَّذ.

## 1. النطاق ووحدة التجربة

- تشمل الخطة UC-01..08: اختبار نشر/اتصال واحد، وسبع آليات كشف/تكامل. لا تُسمّى جميعها اختبارات كشف هجمات.
- عشر محاولات مقاسة **لكل سيناريو ولكل نظام تشغيل مشمول**، بعد محاولة تمهيدية مستبعدة ومعلَّمة `PILOT`. حالات FIM: إنشاء وتعديل وحذف، عشر لكل نوع. لا يُستبدل فشل بمحاولة ناجحة؛ تُحفظ جميع المحاولات.
- ساعة متصلة على الأقل من النشاط الطبيعي الموصوف لكل ملف إعداد اختباري ولكل جهاز لتقييم الإنذارات الكاذبة. يمكن مشاركة الساعة بين الآليات على الجهاز نفسه دون جمعها مرتين في إجمالي التعرض.
- نطاق Windows الأساسي: الاتصال وFIM. VirusTotal على Windows مشروط بتفعيل مسار التكامل المناسب، وYARA على Windows فرع مستقل غير مثبت (ISSUE-006). لا تُدمج نتائجهما مع Linux.
- UC-09..12 خارج T-10. التنفيذ الآلي للقياس من اختصاص T-11، والإصلاحات الأمنية من T-15؛ هذه الخطة لا تغيّر قواعد `wazuh/` أو إعدادات المعمل.
- أرقام النوافذ والحدود أدناه **قرارات بروتوكول مقترحة قبل الاختبار**، وليست ضمانات أداء من Wazuh أو نتائج سابقة.

## 2. بوابة الجاهزية والسلامة (Preflight)

1. معمل افتراضي مصرح به، لقطة استعادة (Snapshot)، وإمكانية دخول من وحدة تحكم الـVM. لا فحص لشبكة عامة، ولا تنزيل/تشغيل عينات برمجيات خبيثة حقيقية؛ استخدم EICAR أو نص YARA اصطناعياً غير تنفيذي.
2. ثبّت `git commit` ونسخة الإعداد المنشورة وبصمات SHA-256 لملفات القواعد والسكربتات وfeed ونسخ الأدوات. لا تعتبر ملفات المستودع دليلاً على تطبيقها. لا تنشر نسخة `ossec.conf` الخام المحتوية على مفتاح API.
3. راجع [المعمارية](../docs/02_ARCHITECTURE.md) وأعد توثيق الحالة الحية. المرجع التاريخي للوكيلين هو [p04_0.png](../docs/sources/screenshots/wazuh_guide/p04_0.png)، ولـSuricata [p30_0.png](../docs/sources/screenshots/wazuh_guide/p30_0.png). حالة `win1` في اللقطة القديمة disconnected وليست نتيجة للجولة الجديدة. نوع الخادم وإصداره الدقيق والأسماء/الواجهات الحالية تُسجّل من الجهاز، لا تُستنتج من prompt.
4. حدّد مصدر الوقت والمنطقة الزمنية على كل VM والجهاز المولّد للأحداث. سجّل فرق الساعة وعدم يقينه قبل الجولة وبعدها. استخدم UTC بصيغة ISO 8601 مع offset. هدف الجاهزية المقترح: فرق مقاس لا يزيد عن 100 ms؛ إذا تعذر إثباته تبقى نتائج الكشف صالحة لكن الأزمنة بين الأجهزة `TIMING_UNVERIFIED`، لا صفراً.
5. تحقّق من الوكلاء والخدمات وبدء مراقبة FIM بعد المسح الأولي. افحص القواعد المنشورة باستخدام `wazuh-analysisd -t`. استبدل placeholders في نسخة المعمل؛ نجاح فاحص المستودع الذي يحيدها لا يثبت صلاحية النسخة الخام للنشر.
6. افحص حقول عينة JSON فعلية لكل UC قبل القياس، وكذلك مسار السجل وصلاحية القراءة وتدويره والحد الأدنى للتنبيه. لا تغيّر الإعداد في منتصف الجولة. استخدم `wazuh-logtest` لفحص فك الترميز والقواعد عند ملاءمته؛ ناتجه ليس تنبيهاً حياً ولا يقيس الشبكة أو AR [R1، R2].
7. قبل UC-03 راجع توجيه AR لكل نظام وسلامة سكربت الحذف؛ قبل #14 كان التوجيه مزدوجاً؛ الحالي استجابة local واحدة باسم remove-threat.exe مع ملف native مناسب لكل OS وhelper على Linux. المراجعة المستقلة في #17؛ الاعتماد الأصلي ما زال مطلوباً. الحذف لا يُسمح به إلا لملفات الاختبار في VM معزولة وبعد مراجعة مختصة؛ عند غيابها الحالة `BLOCKED` والسبب `SAFETY_REVIEW_REQUIRED`.
8. لا تُعطّل Defender كخطوة افتراضية. إذا سبق Wazuh إلى حجر EICAR فاحفظ دليله وصنّف التداخل `INTERFERED`، ولا تنسب الحذف إلى Wazuh. أي استثناء أمني يحتاج موافقة وتوثيقاً مستقلاً وإعادة الحماية بعده.

أوامر تحقق قراءة فقط، تُشغَّل على **الجهاز المحدد** لا على حاسوب المحلل عشوائياً:

```bash
# Wazuh manager (administrative shell)
sudo /var/ossec/bin/wazuh-control info
sudo /var/ossec/bin/agent_control -l
sudo /var/ossec/bin/wazuh-analysisd -t
date -u '+%Y-%m-%dT%H:%M:%S.%NZ'
# Kali endpoint (separate terminal on Kali)
cat /etc/os-release
systemctl is-active wazuh-agent
getent group wazuh
id
cat /proc/self/loginuid
```

```powershell
# Windows endpoint: administrative Windows PowerShell
Get-Service -Name Wazuh
[DateTimeOffset]::UtcNow.ToString('o')
w32tm /query /status
```

`date` و`w32tm /query /status` يوثقان الوقت/المزامنة ولا يثبتان وحدهما حد 100 ms. استخدم قياسات offset من خدمة الوقت الفعلية؛ لا تفترض وجود chrony أو systemd-timesyncd على كل صورة.

## 3. التسجيل والربط (Ground Truth and Correlation)

### 3.1 سجل المحاولات

أنشئ عند التنفيذ سجل JSONL، سطراً لكل محاولة، خارج المجلدات المراقبة. الحقول التعاقدية التالية مدخلات T-11 المقترحة وليست حقولاً يضيفها Wazuh تلقائياً:

| الحقل | المعنى والقيود |
|---|---|
| `run_id`, `trial_id`, `uc`, `variant`, `phase` | معرفات فريدة؛ `phase` = PILOT / MEASURED / BASELINE / SUPPRESSION_CONTROL؛ لا تعاد الاستفادة من معرف سابق |
| `agent_id`, `agent_name`, `os`, `config_commit`, `config_sha256` | هوية المصدر كنص (احفظ الأصفار البادئة مثل 001)، وإصدار ملف الإعداد المنشور |
| `expected_rule_ids`, `expected_levels`, `target_key`, `source_ref` | المتوقع المحدد قبل التجربة، مفتاح الربط، ومسار/سطر الحدث الخام أو رقم audit serial |
| `t_before`, `t_after`, `t_source`, `source_precision_ms` | وقت قبل الفعل وبعده، ووقت الحدث من المصدر إن كان موجوداً؛ لا تملأ وقتاً مفقوداً بتخمين |
| `t_alert`, `alert_id`, `manager_name`, `alert_ref` | وقت ومُعرّف أول تنبيه نهائي مطابق، ومرجع السطر في ملف الأدلة |
| `t_trigger`, `trigger_alert_id`, `t_ar_done`, `t_ar_observed` | وقت تنبيه تشغيل AR، ووقت إنجاز الفعل الموثق إن توفر، ووقت وصول تأكيده إلى المدير |
| `t_visible`, `poll_interval_ms`, `clock_offset_ms`, `clock_uncertainty_ms` | قياس الظهور إن نُفّذ، ودقة الرصد ومزامنة الأجهزة؛ احتفظ بساعة كل مصدر |
| `window_s`, `late_detected`, `status`, `timing_status`, `ar_status`, `reason`, `evidence_refs` | قرارات التصنيف والأسباب والأدلة، بما فيها الفشل والتدخلات |

استخدم `null` للقيمة غير المقاسة، و`NOT_APPLICABLE` في حالة الاستجابة للسيناريو الذي لا يملك AR. لا تستخدم 0 للدلالة على غياب زمن أو عينة.

### 3.2 قواعد الربط

- FIM/VT/YARA: معرف الوكيل + المسار الفريد للمحاولة + نوع الحدث/المرحلة؛ البصمة وحدها لا تكفي لأن عشر نسخ EICAR تحمل البصمة نفسها. تحقّق من المسار كما ورد فعلياً في JSON: `syscheck.path` أو `data.virustotal.source.file` أو `data.yara_scanned_file`.
- auditd: معرف الوكيل + audit serial + PID/AUID/الأمر ونافذة المحاولة؛ لا تستخدم `100210` وحدها لأن `sudo` أيضاً red في القائمة الحالية.
- HTTP: علامة `trial_id` في URL، مع عنواني المصدر والوجهة ووقت سجل Apache. تأكّد في PILOT من حفظ العلامة بعد فك الترميز.
- Suricata: زوج IP/المنافذ + نافذة المسح + `flow_id` و`signature_id` عند توفرهما؛ لا يكفي تنبيه 86601 لا علاقة له بالمسح.
- العمليات: الوكيل + PID + المنفذ في سطر عملية `nc` الفعلية + نافذة المحاولة. لا يكفي وجود العبارة في سطر shell أو أداة اختبار.
- عند تكرار التنبيهات اختر أول تنبيه نهائي مطابق، واحفظ عدد البقية. إزالة تكرار السجل تكون بمفتاح `(manager_name, alert_id)`، مع مرجع السطر. `rule.firedtimes` ليس عدد محاولات التجربة.
- لا تستنتج ترتيباً سببياً من ترتيب وصول السطور فقط. عند تعذر الربط أو التباس عدة أحداث، سجّل `AMBIGUOUS` ولا تختَر الأقرب زمنياً تلقائياً.

### 3.3 ملف الأدلة

المصدر الأساسي للتنبيه هو `/var/ossec/logs/alerts/alerts.json` على المدير [R1]. احفظ نافذة الجولة والسجلات المدورة التي تغطيها، لا تعتمد على `tail` بعد انتهاء التجربة. احفظ سجلات المصدر وAR على الجهاز، ولقطات الشاشة المكمّلة، وmanifest للإعداد والوقت، وبصمات الأدلة. لا تمسح سجلات النظام لإعادة ضبط التجربة.

مجلد التسليم المقترح عند توفر أدلة منقّحة: `docs/lab/evidence/UC-XX/<run_id>/`. هذا مسار مستقبلي، وليس ادعاءً بوجود أدلة جديدة. احفظ الخام الحساس في مساحة خاصة مع صلاحيات مقيدة؛ انشر نسخة منقحة بلا أسرار أو محتوى ملفات شخصية. وثّق التنقيح حتى لا تُفقد مفاتيح الربط.

## 4. تعريف المقاييس دون خلط الطوابع الزمنية

- **`t_source`**: وقت الفعل من سجل المصدر، إن وُجد وله معنى موثَّق. لا تستخدم `syscheck.mtime_after` كبديل عام عن وقت إنشاء/حذف حدث FIM.
- **`t_alert`**: حقل `timestamp` في تنبيه المدير النهائي. لا تفترض أن `@timestamp` في الفهرس هو وقت الإدخال؛ قد يكون تمثيلاً للوقت نفسه. لا تحسب MTTD بطرح الاثنين [R1].
- عند عدم وجود وقت مصدر موثوق، سجّل `t_before` و`t_after` حول الفعل. اعرض مجال التأخير `[t_alert - t_after, t_alert - t_before]` مع عدم يقين الساعة؛ واعرض `t_alert - t_before` فقط باسم **زمن من بدء الفعل (Action-to-alert upper estimate)**، لا باعتباره وقت الحدث الدقيق.
- **معدل الكشف (Detection Rate)** = `DETECTED / (DETECTED + MISSED)`، لكل UC/variant/OS على حدة. المقام محاولات ذات حدث إيجابي مثبت. UC-01 له معدل اتصال وظيفي مستقل، وليس معدل كشف هجوم.
- **متوسط زمن الكشف (MTTD)** = متوسط `t_alert - t_source` للمحاولات المكتشفة ذات توقيت موثوق ومتجانس التعريف فقط. اعرض `n_timed` والوسيط والحدين الأدنى/الأقصى بجانبه. عدم الكشف لا يصبح زمناً صفرياً ولا يدخل المتوسط؛ اعرضه مع نافذة الرصد. عشرة اختبارات لا تثبت نجاحاً عاماً 100%.
- **زمن AR الفعلي** = `t_ar_done - t_trigger` عندما يوجد دليل إنجاز مؤرَّخ مستقل. **تأخير تأكيد AR لدى المدير** = `t_ar_observed - t_trigger` وهو يشمل جمع/نقل التأكيد؛ لا تسمّه زمناً لتنفيذ السكربت وحده. لا توجد حالياً علامات دقيقة لبداية/نهاية كل سكربت، لذلك قد يبقى الزمن الفعلي غير مقاس.
- **نجاح AR** = عدد الإجراءات المثبتة الناجحة / عدد التنبيهات المطابقة التي يجب أن تشغّل AR وفق الإعداد. التشغيل الفاشل أو المفقود يُحسب في المقام؛ لا تقتصر على السكربتات التي بدأت. اعرض كذلك اكتمال السلسلة من الحدث الأول حتى إثبات الاستجابة.
- **زمن الظهور** اختياري: أول وقت يُرى فيه التنبيه باستعلام دوري مستقل (`t_visible`) ناقص `t_alert`، مع فترة polling ودقة المزامنة. لا تستخرجه من لقطة ثابتة أو تفترض وجود حقل ingest.
- **الإنذارات الكاذبة لكل ساعة (FP/hour)** = عدد التنبيهات الأمنية المصنفة كاذبة / ساعات النشاط الطبيعي المرصودة. لا تقسّم على كل التنبيهات ولا تسمِّ ذلك FPR. معدل `FPR = FP/(FP+TN)` يُحسب فقط لتجارب سالبة معدودة ذات تعريف TN واضح.
- FIM على تعديل مشروع هو كشف صحيح لتغير ملف، لا اتهام ببرمجية خبيثة. و`nc -h` المصرّح به قد يطابق سياسة red بشكل صحيح بينما يكون إنذار تهديد كاذباً في الاستخدام العملي؛ اعرض دقة مطابقة السياسة وملاءمة الإنذار الأمني منفصلتين.
- فرق سالب بين وقتَي حدث وتنبيه موثوقين، أو مصدر بلا timezone، أو ساعة قفزت أثناء التجربة = `TIMING_INVALID` يحتاج مراجعة؛ لا تحوّله إلى صفر. أما الحد الأدنى السالب لمجال `t_before/t_after` فقد يعني أن التنبيه سبق انتهاء الأمر، وليس خطأ ساعة بالضرورة؛ يُعرض المجال وعدم يقينه كما هما دون اعتباره زمناً دقيقاً. دقة عرض النتائج لا تتجاوز أضعف دقة مصدر أو ساعة.

## 5. جدول التنفيذ والقرارات المسبقة

| UC | السيناريو / التنبيه النهائي المتوقع | نافذة الرصد المقترحة | الاستجابة |
|---|---|---|---|
| UC-01 | عودة الوكيل إلى active مع حدث تحقق مستقل | 300 s | لا AR |
| UC-02 | إضافة/تعديل/حذف: 554/550/553 أو القاعدة المخصصة التابعة للمجلد | 120 s لكل فعل | لا AR مطلوب لقياس FIM |
| UC-03 | 87105 L12 ثم 100092 L12 مع إثبات الحذف؛ 100093 فشل | 300 s للكشف، ثم 120 s من 87105 للاستجابة | حذف ملف الاختبار فقط |
| UC-04 | 86601 L3 للنمط المعتمد في PILOT؛ أي اختلاف مُسجّل قبل القياس | 120 s بعد نهاية المسح | لا AR |
| UC-05 | 100210 L12 للأمر red المحدد | 120 s | لا AR في الإعداد الحالي |
| UC-06 | 31168 L15 لنمط Shellshock في HTTP | 120 s | لا AR |
| UC-07 | 108001 L12 بعد محفز FIM الموافق للنظام | 120 s للمحفز ثم 120 s للتأكيد | فحص، لا حذف |
| UC-08 | 100051 L7 لعملية مستمعة فعلية | 120 s، مع إبقاء العملية 90 s | لا AR |

الحدود ليست شروط نجاح يجب تعديلها حتى تنجح النتائج. تُثبَّت قبل المحاولات المقاسة، وأي تعديل ينشئ `run_id` جديداً. للكشف ذي المرحلة الوسيطة، تُسجّل أزمنة المراحل منفصلة؛ لا تخلط 100301 (حدث ملف) مع 108001 (نتيجة YARA).

حالات المحاولة: `DETECTED`، `MISSED` (حدث صحيح ولا تنبيه مطابق ضمن النافذة)، `BLOCKED` (لم يبدأ بسبب متطلب مفقود)، `INVALID` (فشل توليد الحدث أو تلف القياس)، `INTERFERED` (تدخل أداة أخرى)، `AMBIGUOUS`. حالة `LATE` علامة إضافية للتنبيه بعد الموعد: يبقى MISSED في المعدل ضمن النافذة، وتُعرض الاكتشافات المتأخرة منفصلة. `SUPPRESSION_CONTROL` تجربة مستقلة للكبت لا تدخل معدل الكشف الرئيسي.

لا تستبعد انقطاع التكامل/نفاد حصة API بعد حدث صحيح من المقام لتحسين النتيجة: يسجل MISSED مع السبب. إذا عرف العائق **قبل** توليد الحدث فهو BLOCKED. اعرض أعداد الحالات المستبعدة وأسبابها بجانب المقام؛ لا تعدّل معيار الاستبعاد بعد رؤية النتائج.

## 6. بروتوكولات حالات الاستخدام

### UC-01 — نشر الوكلاء والتحقق من الاتصال

المرجع: [دليل النشر](../docs/lab/UC-01_agent_deployment.md). **المتطلبات:** تثبيت الوكيلين والتحقق من هويتهما وخدماتهما؛ لا تُثبّت الحزم أو تُعد تسجيل الوكلاء عشر مرات.

1. تحقق من إصدار/هوية الوكيل المنشور وسجّل ذلك كفحص نشر واحد لكل OS. إن كان الوكيل غير مثبت، اتبع دليل النشر بعد تأكيد الحزمة، وسجّل زمن التثبيت منفصلاً عن إعادة الاتصال.
2. كرّر عشر دورات إعادة تشغيل خدمة الوكيل فقط، جهازاً واحداً في كل مرة، خارج جولات باقي UCs. سجّل `t_before` و`t_after` حول `sudo systemctl restart wazuh-agent` على Kali أو `Restart-Service -Name Wazuh` على Windows.
3. راقب `agent_control -l` على المدير كل خمس ثوانٍ حتى 300 s، وسجّل آخر رصد قبل العودة وأول رصد بعدها. بقاء active في اللوحة مؤقتاً لا يثبت اتصالاً جديداً؛ افحص سجل بدء الخدمة على الجهاز، ثم نفّذ إنشاء ملف تحقق فريد وفق UC-02 بعد جاهزية FIM واربط تنبيهه الجديد.
4. النجاح الوظيفي يحتاج الخدمة عاملة + active + حدثاً جديداً مطابقاً من الوكيل الصحيح. إذا لم يكن FIM جاهزاً، دوّن الاتصال والتحقق النهائي كحالتين مستقلتين، ولا تنسب فشل FIM تلقائياً إلى التسجيل.

**القياس/الضبط:** زمن إعادة الاتصال المرصود وحده يشمل polling؛ لا تسمّه MTTD. وثّق تأخر ظهور disconnected أثناء توقف الخدمة في تجربة صيانة منفصلة إن أُجريت، ولا تعتبره تهديداً. **التنظيف:** اترك الوكيلين active ولا تحذف agent keys أو تعِد تسجيلهما.

### UC-02 — مراقبة سلامة الملفات (FIM)

المرجع: [دليل FIM](../docs/lab/UC-02_fim.md)، وملفات `wazuh/agents/*/ossec.conf.d/10-syscheck-dirs.xml`، والقواعد المحلية المنشورة.

**المتطلبات:** مجلد موجود ومراقب، صلاحية كتابة، اكتمال مسح FIM الأولي. ضع سجلات المشغّل خارجه. على Linux، `/home/kali/abdul` مرتبط أيضاً بقواعد YARA في المستودع؛ لذلك قد تكون القواعد النهائية 100301/100300 L7 بدلاً من 554 L5/550 L7. حذف الملف متوقع 553 L7. اختر قبل القياس القائمة الدقيقة حسب المسار والإعداد، لا تشترط ظهور الأب والابن كسطرين منفصلين. قواعد Windows تُراجع بالطريقة نفسها.

1. عرّف `FIM_DIR` من الإعداد الفعلي، و`TRIAL_ID` فريداً بأحرف ASCII وأرقام وشرطات فقط. اختبر مسارات الاختبار على أنها ملفات عادية داخل المجلد المتفق عليه.
2. أنشئ ملفاً نصياً باسم المحاولة، احفظ وقتَي ما قبل/بعد الإنشاء، وانتظر التنبيه أو نهاية 120 s.
3. بعد إثبات الإضافة إلى قاعدة FIM، عدّل محتواه مرة واحدة وسجّل توقيتاً مستقلاً، ثم انتظر حتى 120 s. إذا لم يُثبت وجود الملف في FIM فالتعديل اللاحق BLOCKED، ولا تخفِ فشل الإنشاء.
4. بعد رصد التعديل/توثيق حالته، احذف **ملف التجربة وحده** وسجّل توقيتاً مستقلاً، ثم انتظر حتى 120 s. نفّذ عشر دورات؛ كل فعل صف مستقل.

أمثلة أفعال مفردة؛ ليست سكربتاً يُشغّل الأسطر الثلاثة متتابعة. نفّذ التسجيل والانتظار بين الأفعال:

```bash
# Kali; run in a dedicated test shell, one phase at a time
set -e

test -d "$FIM_DIR" || exit 1
```

```powershell
# Windows; set verified $FimDir and unique $TrialId first
$ErrorActionPreference = 'Stop'
```

**الضبط السالب:** القراءة فقط لنفس الملف، وإنشاء ملف خارج جميع مسارات FIM بعد التحقق منها؛ لا تتوقع تنبيه تغيير لهذا الهدف. التعديل المصرّح به داخل المجلد ليس FP لـFIM. **القياس:** §4 باستخدام المجال الزمني للفعل إذا غاب وقت المصدر؛ AR غير منطبق على نتيجة FIM حتى لو شغّل المجلد YARA. **التنظيف:** تحقق من غياب ملفات الجولة فقط واحتفظ بأدلة تنبيهات الحذف.

### UC-03 — VirusTotal والاستجابة بحذف ملف الاختبار

المرجع: [دليل VirusTotal](../docs/lab/UC-03_virustotal_active_response.md)، و`20-virustotal-integration.xml`، و`30-active-response-remove-threat.xml`، و[R4، R8].

**المتطلبات:** اجتياز بوابة السلامة §2، وتحقق حصة API والاتصال ونسخة AR المنشورة. الإعداد الحالي يختار 100200/100201 لمسار Linux؛ وجود سكربت Windows لا يجعل Windows مشمولاً تلقائياً. الفرع Windows BLOCKED حتى التحقق من محفزاته وتوجيهه؛ لا تغيّر `<group>` لتشمل كل syscheck أثناء القياس.

1. استخدم EICAR غير التنفيذي من [السكربت الموجود](../scripts/attack-emulation/eicar_test.sh)، بعد مراجعة محتواه. اسم الملف داخله ثابت `eicar.com`؛ مرّر له مجلد محاولة فريداً تحت المسار المراقب، وتحقق في PILOT من أن مراقبة المجلدات الفرعية تعمل قبل بدء العشر محاولات. البديل اسم ملف فريد عبر مشغّل معتمد، لا إعادة استخدام المسار نفسه أثناء وجود أحداث معلقة.
2. احفظ محتوى الاختبار وبصمته المتوقعة **قبل** وضعه في المسار المراقب؛ قد يحذف بسرعة. لا تعدّل محتوى EICAR لإضافة trial_id؛ ضع المعرف في المسار. سجّل فعل الكتابة فقط في التوقيت، لا تنزيل ملف من الإنترنت أو تثبيت الحزم.
3. انتظر محفز FIM 100201 أو 100200 L7 الموافق للفعل، ثم 87105 L12 خلال 300 s من الفعل. اربط بمسار الملف ومعرف الوكيل؛ لا تقبل تنبيه VT من جولة قديمة تحمل البصمة نفسها.
4. منذ 87105، انتظر حتى 120 s بحثاً عن 100092 L12 مع سجل AR والغياب الفعلي للملف. تحقق مستقلاً من حالة الملف بفاصل رصد ثابت مسجّل (مثلاً ثانية)، واحفظ آخر وقت وجود وأول وقت غياب. 100093 دليل فشل، و553 وحده لا يثبت أن AR هو من حذف.
5. لا تحذف يدوياً أثناء نافذة الرصد. بعد انتهاء القياس، أي تنظيف يدوي يوسم `CLEANUP` ولا يُحسب استجابة ناجحة. أعد المحاولة بمسار جديد عشر مرات، وفق الحصة الفعلية.

**الحدود/الضبط:** API العام موثق بحد 4 طلبات/دقيقة و500/يوم [R4]؛ افصل محاولات البداية 60 s على الأقل، وراقب الطلبات الأخرى وإعادة المحاولة؛ هذا التباعد لا يضمن وحده عدم تجاوز الحصة. اختبر ملفاً نصياً سليماً منفصلاً: عدم معرفة بصمته ليس إثبات نظافة، لكن لا ينبغي حذفه باعتباره VT-positive. لا تعطل الاتصال عمداً ضمن الجولة الرئيسية.

**القياس:** زمن فعل→87105، ثم تأخير تأكيد AR إلى 100092، ومجال زمن اختفاء الملف مع إسناد السبب. نتيجة السكربت النصية وحدها لا تكفي: `rm -f` قد ينجح لملف غائب أصلاً. **التنظيف:** ملفات التجربة فقط، بلا تغيير الحماية أو المفتاح في المستودع.

### UC-04 — كشف الشبكة عبر Suricata

المرجع: [دليل Suricata](../docs/lab/UC-04_suricata_nids.md)، و`40-localfile-suricata.xml`؛ الدليل التاريخي المذكور في المعمارية لا يحل محل سجل الجولة.

**المتطلبات:** واجهة فعالة يمر بها الترافيك فعلاً، HOME_NET صحيح بلا تكرار، تغذية قواعد مثبتة البصمة، `suricata -T` ناجح، وأحداث eve.json تصل إلى الوكيل. جهاز توليد المسح مختلف عن الهدف ضمن المعمل؛ لا تفترض أن حركة localhost مرئية للحساس على eth0.

1. في PILOT نفّذ مسحاً واحداً محدد الهدف والمنافذ بعد الموافقة، وتحقق من وجود `event_type=alert` في `/var/log/suricata/eve.json` للتوقيع المتوقع. ثبّت `signature_id` والاسم والتوقيع/عتبته ونافذة الكبت. إذا لم يولد التوقيع مع الفعل المختار فالسيناريو غير جاهز؛ لا تعد نجاح ping إثبات كشف.
2. نفّذ عشر عمليات مسح منفصلة بالإعداد نفسه، مع حفظ مخرجات nmap ووقتَي البداية والنهاية والمصدر والهدف والمنافذ. السكربت الموجود `nmap_scan.sh` يفحص المنافذ الافتراضية؛ لا تشغله دون مراجعة النطاق، ولا تخلط جولات ذات نطاقات مختلفة.
3. اربط تنبيه eve بالتنبيه النهائي في المدير (المتوقع في هذا المشروع 86601، وافحص المستوى المنشور في PILOT) بواسطة signature/flow/العناوين والنافذة. انتظر 120 s بعد نهاية المسح؛ لا تُعِد المسح قبل انتهاء فترة الكبت المحددة في التوقيع.
4. سجّل طبقتين منفصلتين: هل ولّدت الحركةُ حدث Suricata المتوقع؟ وهل وصل هذا الحدث إلى Wazuh؟ حدث Suricata موجود بلا تنبيه Wazuh = فشل تكامل؛ حركة اختبار مثبتة تستوفي التوقيع بلا حدث Suricata = فشل كشف حسّاس، لا محاولات مستبعدة.

**القياس:** زمن `eve.timestamp`→`t_alert` يسمى **تأخير تكامل Suricata→Wazuh** لا MTTD من بدء الهجوم. زمن بدء المسح→التنبيه قياس نهاية إلى نهاية مستقل، لأن إصدار توقيع المسح قد يتطلب عدة حزم. **السالب:** طلب HTTP عادي إلى خدمة المعمل دون مسح؛ راجع أي تنبيه بدلاً من افتراض غيابه. **التنظيف:** أوقف مولّد المسح، ولا تحذف eve.json أو تغيّر القواعد.

### UC-05 — auditd وقائمة الأوامر المصنّفة

المرجع: [دليل auditd](../docs/lab/UC-05_auditd_malicious_commands.md)، و`suspicious-programs`، و[R7].

**المتطلبات:** auditd عامل، قواعد execve محملة، AUID جلسة المستخدم يطابق 1000 وفق الإعداد، وشرط المجموعة موثق (ISSUE-031). قيمة UID الفعلية لا تكفي لإثبات AUID. تحقق من الاسم المفكوك `data.audit.command`، فقد يختلف عن الاسم في سطر الأوامر أو هدف symlink.

1. افحص `sudo auditctl -l` والـloginuid و`command -v nc` في مرحلة الجاهزية، لا في وسط المحاولة. افصل أحداث sudo الناتجة عن التجهيز لأنها red أيضاً.
2. نفّذ `nc -h` مرة واحدة من جلسة المستخدم المطلوبة، بلا فتح اتصال أو مستمع، واحفظ توقيت البداية والنهاية وحالة الخروج. بعض نسخ nc تعيد خروجاً غير صفري للمساعدة؛ المعيار هو إثبات execve لا رقم الخروج وحده.
3. استخرج سجل الحدث من `/var/log/audit/audit.log` واربط سجلات SYSCALL/EXECVE ذات audit serial نفسه مع PID/AUID/الأمر. ابحث عن 100210 L12 خلال 120 s وأعد ذلك عشر مرات منفصلة.
4. إذا كان nc لا يطابق اسم القائمة، سجّل عدم التطابق قبل القياس كعائق إعداد؛ لا توسّع القائمة سراً. لا تستخدم `netcat_tests.sh` لهذه التجربة لأنه يضيف اختبار مستمع UC-08 أيضاً.

**السالب:** عشر عمليات `whoami` (yellow في القائمة الحالية)؛ لا يُنتظر لها 100210، مع السماح بسجلات audit الطبيعية. **القياس:** timestamp داخل audit serial→تنبيه 100210 بعد التحقق من المنطقة الزمنية/الدقة؛ لا تنسب تنبيه sudo المجاور إلى nc. **الحد العلمي:** هذا اختبار مطابقة سياسة أسماء أدوات، وليس إثبات أن كل استعمال nc هجوم. **التنظيف:** لا توجد عملية مستمعة ولا ملفات تهديد؛ احتفظ بالسجلات.

### UC-06 — كشف نمط Shellshock دون استغلال فعلي

المرجع: [دليل Shellshock](../docs/lab/UC-06_shellshock.md). **المتطلبات:** خدمة Apache في المعمل ومسار HTTP ثابت **غير CGI**، وصول User-Agent إلى access.log وتكامل السجل مع Wazuh. لا تفعّل ثغرة أو CGI ولا تعدّل الجدار الناري لمجرد الاختبار.

1. نفّذ PILOT بطلب واحد إلى المسار الثابت لتأكيد تسجيل الترويسة وفك الترميز إلى 31168. الطلب أدناه يحتوي نمط اختبار وتعليمة echo فقط، دون قراءة ملفات النظام؛ `LAB_TARGET` عنوان مُتحقق ومصرّح به وليس عنواناً مفترضاً.

```bash
# Approved isolated lab only; target root must be a verified non-CGI resource
: "${LAB_TARGET:?Set the authorized lab host}"
: "${TRIAL_ID:?Set a unique ASCII trial identifier}"
curl --noproxy '*' --max-time 10 --silent --show-error \
  -A '() { :; }; /bin/echo SOC_SHELLSHOCK_TEST' \
  "http://${LAB_TARGET}/?soc_trial=${TRIAL_ID}"
```

2. لكل من عشر محاولات، سجّل وقتَي الطلب ومخرجه وحالته، ثم السطر الخام من `/var/log/apache2/access.log` وفيه علامة المحاولة. انتظر 31168 L15 خلال 120 s واربط بالوكيل والطلب نفسه.
3. إذا انتهى curl بمهلة فقد يكون الطلب وصل: القرار مبني على سجل المصدر، لا خروج curl وحده. صفحة Apache العادية لا تعني فشل الكشف أو نجاح استغلال. لا يُدّعى تنفيذ أوامر عن بُعد.

**السالب:** عشر طلبات للمسار نفسه بعلامات مستقلة وUser-Agent عادي؛ لا يُتوقع 31168. **القياس:** وقت سجل Apache بدقة المصدر (قد تكون ثانية)→التنبيه؛ اعرض مجال الفعل إن احتجت قياساً بدقة أعلى ولا تزعم دقة مللي ثانية من سجل ثوانٍ. **التنظيف:** لا ملفات أنشأها الهدف؛ احفظ سجلات الجولة ولا تمسح access.log.

### UC-07 — سلسلة FIM → فحص YARA → تأكيد النتيجة

المرجع: [دليل YARA](../docs/lab/UC-07_yara.md)، و`40-active-response-yara.xml`، و[R5]. **المتطلبات:** قواعد YARA دائمة المسار، binary قابل للتنفيذ من حساب AR، الملف داخل المجلد الصحيح، ونتائج AR تُجمع فعلياً. Windows مشروط بإثبات التشغيل وليس نجاح النسخة Linux.

1. فضّل **ملف اختبار نصياً سليماً** وقاعدة اختبار واضحة على تنزيل عينات حقيقية. المحتوى الإيجابي المقترح `SOC_T10_YARA_POSITIVE`، والسالب `SOC_T10_YARA_NEGATIVE`. ملف الإعداد الاصطناعي أدناه يحتاج موافقة ونشراً في نسخة قواعد اختبار في المعمل قبل PILOT؛ ليس جزءاً مضافاً فعلياً إلى `wazuh/`، ولا قاعدة Wazuh برقم جديد.

```yara
rule SOC_T10_TestMarker
{
    strings:
        $marker = "SOC_T10_YARA_POSITIVE"
    condition:
        $marker
}
```

2. سجّل ملف الاختبار وقاعدته وبصمتهما، وتحقق بفحص YARA مباشر خارج المجلد المراقب أن الإيجابي يعطي `SOC_T10_TestMarker` والسالب لا يعطيها. استخدم الملف نفسه في AR ضمن **ملف إعداد اختباري مُعلن**، ولا تستبدل قواعد الإنتاج دون موافقة/نسخة احتياطية. إذا لم يُعتمد هذا الإعداد فالفرع الاصطناعي BLOCKED؛ يمكن اعتماد EICAR مع feed الحالي فقط بعد إثبات أنه يطابق قاعدة فيه.
3. أنشئ ملفاً إيجابياً فريداً في مجلد YARA المراقب، واحفظ وقت الكتابة. انتظر 100301 L7 على Linux (أو 100304 على Windows المعتمد) ثم 108001 L12 باسم القاعدة ومسار الملف نفسيهما. كرّر عشر مرات.
4. لفرع التعديل، أنشئ ملفاً سالباً وانتظر دخوله إلى FIM؛ أضف العلامة الإيجابية ثم انتظر 100300 L7 (أو 100303 على Windows) وتأكيد 108001. عشر محاولات مستقلة، غير مدمجة مع فرع الإضافة.
5. احفظ سطر نتيجة YARA على الجهاز وتنبيه المدير. الملف يُفترض أن يبقى؛ الفحص ليس حذفاً. سجل YARA الحالي قد لا يتضمن زمناً دقيقاً للإنجاز؛ استخدم تأخير تأكيد AR من تنبيه FIM إلى 108001، والزمن الفعلي `null` ما لم يوجد مصدر توقيت موثوق.

**السالب:** عشر ملفات دون العلامة الإيجابية؛ لا يُنتظر اسم قاعدة الاختبار. غياب 108001 لا يثبت أن الفحص السالب نُفِّذ بنجاح؛ يلزم دليل تشغيل/خروج، وإلا قيّد الاستنتاج إلى «لا تنبيه مطابق مرصود». **القياس العلمي:** تطابق قاعدة صناعية يقيس صحة خط الأنابيب، لا دقة كشف البرمجيات الخبيثة أو جودة feed. الاختبار بقواعد VALHALLA يسجل منفصلاً مع البصمة والنسخة المحدودة (ISSUE-025). **التنظيف:** ملفات الجولة فقط، وإعادة قواعد ما قبل الاختبار بعد انتهاء جميع محاولات الملف الاختباري مع توثيق الاستعادة.

### UC-08 — مراقبة مستمع Netcat والكبت

المرجع: [دليل مراقبة العمليات](../docs/lab/UC-08_process_monitoring_netcat.md)، و`50-command-process-list.xml`، و`local_rules.xml`، و[R3، R6].

**المتطلبات:** جمع القائمة كل 30 s بحسب الإعداد المنشور، والقاعدة 100051 L7 ذات `ignore=900`. المعنى الرسمي: تجاهل **القاعدة** بعد إطلاقها؛ لا يُفترض أن تغيير PID يتجاوز الكبت. لا تغيّر ignore أو تعِد تشغيل المدير لتسريع الاختبار.

1. تحقق من نوع nc ودعمه للخيارات في PILOT، واختر منفذاً غير مستخدم داخل VM معزولة. من طرفية تفاعلية على الجهاز شغّل مستمعاً بلا `-e` وبلا shell بعيد؛ مثال `nc -l -p "$TEST_PORT"` بعد تعيين المنفذ المعتمد. لا تستخدم غلاف `bash -c` أو timeout يتضمن العبارة نفسها ويخلق تطابقاً مضللاً في قائمة العمليات.
2. من طرفية أخرى، تحقق من وجود socket مستمع وPID بواسطة `ss -lntp` (بصلاحية تسمح بعرض العملية) و`ps -e -o pid,uname,command`؛ احفظ سطر nc الفعلي ووقت أول تحقق. عبارة في سطر wrapper ليست دليلاً على مستمع.
3. أبق العملية 90 s، انتظر تنبيه 100051 حتى 120 s من بدء الفعل، ثم أوقف العملية المحددة بـCtrl-C أو PID موثق؛ لا تستخدم `pkill nc`. سجل 100210 من auditd إن ظهر كحدث جانبي، لا كنجاح UC-08.
4. قبل **كل** محاولة مقاسة، بما فيها الأولى بعد PILOT، انتظر 930 s على الأقل من أحدث تنبيه 100051 على المدير وتحقق من عدم إطلاقها مجدداً في هذه الفترة. الحد = 900 s للكبت + 30 s احتياط البروتوكول؛ راقب بقية الأجهزة حتى لا تلوّث النافذة. كرّر عشر محاولات. تتطلب الجولة أكثر من ساعتين؛ وثّق هذا بدلاً من ضغط التجارب داخل الكبت.
5. نفّذ تجربة إضافية واحدة منفصلة `SUPPRESSION_CONTROL`: مستمع جديد بعد تنبيه ناجح وقبل انقضاء 900 s مع إثبات وجوده في القائمة. راقب الكبت وسجّله كخاصية تشغيلية، لا تضع غياب التنبيه في مقام المحاولات المستقلة. إذا وُلّد الحدث عرضاً داخل الكبت في الجولة الرئيسية، سجّل خرق البروتوكول ولا تُخفه.

**السالب:** عمليات عادية دون مستمع nc أثناء baseline؛ تطابق القاعدة لنص في سطر عملية غير مستمعة يراجعه المحلل كإنذار كاذب. **القياس:** وقت بدء العملية/مجال الفعل→التنبيه، ويشمل انتظار دورة الجمع؛ لا تتوقع تأخيراً صفرياً أو 30 s كحد مضمون. **التنظيف:** إيقاف مستمع الاختبار والتحقق من إغلاق منفذه.

## 7. النشاط الطبيعي وجدول التقرير

### 7.1 ساعة مرجعية موصوفة لكل جهاز/ملف إعداد

سجّل بداية الساعة ونهايتها، وتوقفات الجمع وأفعال المستخدم، دون اختبارات موجبة في الساعة نفسها:

| الفترة المقترحة | النشاط المصرح به |
|---|---|
| 0–15 دقيقة | الجهاز خامل مع خدماته المعتادة؛ تحقق أن جمع السجلات مستمر |
| 15–30 دقيقة | إنشاء/قراءة/تعديل مستندات نصية عادية في مسارات الاختبار الموافق عليها |
| 30–45 دقيقة | طلبات HTTP عادية إلى خادم المعمل وعمليات whoami؛ لا مسح منافذ |
| 45–60 دقيقة | إدارة عادية معتمدة؛ إن استُخدم sudo أو nc للمساعدة فسجّل القصد وميّز مطابقة red عن إنذار تهديد صحيح |

على Windows استخدم المكافئ المتاح للأعمال المكتبية، وسجّل البرنامج/الأمر الفعلي بدل افتراض وجود sudo أو nc. مدة تعرض الجهاز لا تصبح ثماني ساعات لأن ثماني آليات تراقبه. عند تغيير إعداد YARA إلى ملف صناعي، الساعة الناتجة تخص ذلك الملف لا feed الإنتاج. إذا انقطع الجمع، أعد ساعة كاملة أو أعلن مدة الرصد الفعلية؛ لا تحسب الانقطاع زمناً سليماً بلا FP.

كل تنبيه خلال الساعة يراجعه محلل بشري مع سجل النشاط: `EXPECTED_CHANGE` / `POLICY_MATCH_BENIGN` / `FALSE_THREAT_ALERT` / `UNEXPLAINED`. احفظ أيضاً `policy_match` و`is_false_threat_alert` كحقلين مستقلين: قد تكون مطابقة السياسة صحيحة مع إنذار تهديد كاذب. بسط FP/hour هو التنبيهات المحسوم فيها `is_false_threat_alert=true` دون عد مزدوج، أما غير المحسوم فيبقى منفصلاً. لا تُصنِّف تنبيهاً غير مفسر كاذباً لمجرد أن التجربة تسمى baseline؛ أوقف النشاط عند الاشتباه بحادثة فعلية. انشر عدد غير المحسوم منفصلاً. لا تعد الآثار المكررة للحدث محاولات مستقلة؛ اعرض معدل التنبيهات الخام والعدد بعد التجميع بتعريف واضح.

### 7.3 معايير قبول T-10 وتسليم T-11

- T-10 مكتملة **توثيقياً** عندما تغطي UCs الثمانية: المتطلبات، الأفعال، الربط، المتوقع، النوافذ، الضبط، السلامة والتنظيف؛ ومعها تعريف المقاييس والحقول والتمييز بين NOT_RUN والنتائج.
- قبول النظام في المعمل قرار لاحق: خطة كاملة لا تعني أن كل UC جاهزة أو نجحت. لا تُغلق ISSUE-019 ولا تُفتح T-23 على أساس نتائج متخيلة.
- T-11 يحتاج **سجل المحاولات + السجلات الخام + alerts.json + manifest الوقت/الإعداد**؛ alerts.json وحده لا يحصي المحاولات التي لم تُكتشف ولا يضمن وجود وقت المصدر أو وقت AR.
- اختبارات أداة T-11 المقترحة: بيانات اصطناعية معلّمة بوضوح تغطي offsets/timezones، قيماً مفقودة، توقيتاً سالباً، JSON تالفاً، تدوير السجل، تكرار معرفات عبر مديرين، محاولتين بالبصمة نفسها ومسارين مختلفين، MISSED/LATE، وكبت Netcat؛ ليست هذه نتائج المعمل.
- التنفيذ التالي: اعتماد الجاهزية/السلامة وملف YARA الاختباري، تنفيذ PILOT ثم الجولات والساعة المرجعية على الأجهزة، مراجعة بشرية للأدلة، ثم إنتاج الجدول والرسم للفصل الخامس. لا يشمل هذا التسليم تنفيذ T-11 أو تغيير سكربتات T-15.
